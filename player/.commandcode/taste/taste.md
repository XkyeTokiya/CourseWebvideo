# 交互
- 用户以简体中文交流,始终用中文回复。Confidence: 0.9
- 绝不在一次写入里输出超长文件:分段写入——首段以哨兵标记结尾,后续 edit_file 用哨兵换下一段加新哨兵,末段移除;长聊天报告同样切分;主动切分,不等掉线教训(用户明示的长期指令)。Confidence: 0.95
- 执行轮次要紧:一次性交付物、只做阶段必需读取、一行过程叙述、到 checkpoint 即停;被指太慢就砍评论立即交付。checkpoint 决策以单个编号列表呈现,每项可仅以数字/关键词回答;用户只答需决策项,未回应项视为按原方案接受并继续;开放判断项用户常整体放权(“按照你的想法来”)——又一实例:"按照你的推荐全部处理"对整批建议一次放行;接管判断、开工前一句披露所定决策,无阻塞问题即直接开始制作,不再追加确认轮——但整体放权与原始指令里"执行完整流程"只覆盖已获授权阶段内的判断项,不构成跨过硬 checkpoint 连续推进多阶段制作的许可:episode 制作中未等确认就连做 script→outline→脚手架并派发并行制作 agent,被厉声叫停("是谁允许你一直制作的"),处置为立即冻结全部写操作(含后台任务不再推进)、如实盘点已完成/进行中/后台状态、以编号裁决列表逐项交用户(每项可仅数字回答),未获放行前不做任何制作动作。Confidence: 0.9
- 明确暂停指令("暂停任务"):只回简短确认 + 一行状态保存说明,立即停止,不再有任何工具调用,直到用户明确说继续。Confidence: 0.9
- 视觉验证归用户:代码级检查全绿(episode:check / typecheck / lint / audio:extract 分段计数 / build 及静态审计)即交付验收指针(播放 URL + 看哪屏 + 看什么)并停;不开浏览器、不截图、不迭代视觉细节;用户喊停验证立即停,待修项落 scoped commit 后继续批次;验证欠账写进提交信息与进度报告并给出补审时点。Confidence: 0.95

# 工作方式
- Windows 环境:shell_command 执行 cmd.exe——PowerShell cmdlet 走专用 powershell 工具;git 多行提交信息用两个 -m 或 scratchpad 文件 + `git commit -F <file>`(here-string 位置传参会被当 pathspec 静默失败);细节见 [environment/taste.md](environment/taste.md)。Confidence: 0.9
- 证据先行:bug 先交证据支撑的根因诊断(什么坏了/在哪/为何自检没拦住),确认后再改文件;不把文档承诺当真——契约声明与启发式都对照实际成品工件实证复核;被质疑("请你重新思考")时真正重新审视,愿意基于证据推翻自己的方案。Confidence: 0.9
- 方案先行与严格执行:规则/设计改动先列多个备选 + 明确取舍 + 有理由的推荐,不预设唯一修法;≥3 文件或契约/规则改动先确认精确编辑范围再交整合书面方案评审,1-2 文件小改 checkpoint 一句确认即可,通过后严格执行、禁止静默私自优化——超出方案字面的改进必须经坦白逐项自审计(照做项 vs 每处偏离及性质、留待用户裁决的点)浮出水面。Confidence: 0.8
- 上下游边界:契约/规则/输出改动只落本仓库(下游);上游 skills 与已完工工件冻结只读;再生成最小扰动(已批准文案不动);需超出下游权限时向用户提出冲突,由用户上游协商带回授权,绝不单方面偏离或重新解释冻结契约。Confidence: 0.9
- See [workflow/taste.md](workflow/taste.md) · [visual-design/taste.md](visual-design/taste.md) · [courseplay/taste.md](courseplay/taste.md) · [environment/taste.md](environment/taste.md) ——主题分包,进入对应领域工作前按需读取。Confidence: 0.9

# Taste 维护
- 用户会实际审计 taste 是否被遵循,发现失守时要求对 taste 系统本身做结构化诊断与修复,而非重申规则(本源案例:主文件被精简成一行指针、83 条沉在二级类目,新会话自动注入量归零→批准分包重构)。批准的布局:只有主 taste.md 在新会话自动注入,故主文件只内联跨场景高频核心、每类 ≤5 条(防类别被整体移出再次归零),长尾细节留主题分包按需读取;修剪取向是合并去重而非全保留或激进删减。Confidence: 0.8
- Taste 内容一致性:用户会主动发起 taste 清理与既有条目的重复/冲突审查(案例:subagent 相关四条目;又一轮全量清理,明示"先确认现状再动手");审查须分类报告——同一规则的跨条目/条目内复述、字面相反但可调和的张力(写明调和方式)、真冲突、混入现行条目的过期协商记录(已被取代的旧约定应从现行条目剥离)、lint 可检出的损坏条目,并附逐项合并/改写建议与编号待决策项,不擅自改写。Confidence: 0.75
- 系统文件重构/清理的执行纪律:动手前先把原目录完整备份到 scratchpad——适用于任何 taste 改动,不限于整体重构(用户明示“修改之前对taste进行打包备份”);方案获用户批准后由 agent 直接重写落盘,不产出草案等人工粘贴;改完跑 `npx taste lint --all` 校验(裸 `taste lint` 会报需要显式范围)并汇报逐文件改动摘要。Confidence: 0.85
- taste 文件格式硬约束(lint 强制,改文件前先知道):条目用中文、每条一行 bullet、以 Confidence 分数结尾;主文件不得有引言/注释行、不得留无条目的空类目标题;分包指针也要写成合法学习条目(如 See [x](x) ——说明。Confidence: 0.9)。Confidence: 0.85
- 语义强度校准:用户会把"过度要求"当作 taste 质量维度主动审查(主动要求做语义级分析、识别要求强度/触发面超出必要的条目——如不成比例的停机上报条款、不可验证的绝对化禁令、缺重大性/类型门槛的全量汇报义务、单实例数值固化为永久规则——用户对该维度明示"必须处理");随后对全部修订建议一次整批批准落盘;写新条目或修订时保持强度与风险成比例、表述可操作可验证;实例数值(px/百分比/秒)默认仅属该实例参考,写入 taste 前须转为可迁移的语义约束或显式标注适用范围,不自动法律化;例外:涉及模型资费的停机/上报条款不算过度,用户明示必须如此保留。Confidence: 0.85
