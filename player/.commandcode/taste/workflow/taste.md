# Workflow
- Episode 生产流程:terse kickoff → 自助文档化(CLAUDE.md → production skill → 开工预检)→ 开工即把 project.json 翻到可预览态(合法取值与门控口径见 courseplay 分包;停在 planned 用户无法预览)→ 逐章交付报告(commit hash、绿勾清单含分段计数=拍数、机制与逐拍节奏、待提供素材、验收指针与下一章预览)→ 用户"继续"放行;每章先在 entry.tsx 注册并递增 project.json 完成数再跑链;章批次验证链(episode:check / typecheck / lint / audio:extract -- --episode <ep> / build)一次通过后落 scoped commit。Mode A(逐章制作·逐章确认)长期默认;批处理节奏由用户在节奏 checkpoint 指定,按所选执行并在统一验收节点停;多章批次:一次确认概述各章设计 → 同轮写完全部章文件 → 跑一次全链 → 单个合并 commit → 一份分章报告+共享验收指针;被既有基线债(如 tools/ 既有 lint 报错)阻塞时:先按改动范围归因确认非本次引入,再单跑其余环节确认交付物绿,基线债备案交用户裁决。Confidence: 0.8
- 完整制作任务的完成汇报结构(用户明示):制作完成后先做必要校验,再按固定四项汇报——修改或新增的文件、运行过的命令、校验结果、仍需人工处理的问题(待提供素材/未决项);任务指令带显式约束/禁令时,报告逐项披露遵从落实情况供用户审计(episode-06:分段写入段数、辅助文档"仅作上下文"的用法声明、被禁止豁免项的拍切分口径披露)。Confidence: 0.75
- 验收修订处理:用户"继续"放行时先把 outstanding 的用户指示验收修订落成独立 scoped commit,再开下一批;编舞偏离按授权的 step→element 映射原样实现,偏离点代码标注(如"本章偏离口播切分(Checkpoint 已授权)"),outline 记录授权偏离及理由(仅本章豁免);用户指令的屏上文本删除:narrations/拍数逐字节不变,删 TSX 元素及整个 CSS 块(无死样式),同步 outline.md 所有提及处(章节块/步骤表/调度表),记录"**用户修订(验收指示)**"来源行,被移语义归入既有内联元素不留洞,重跑 typecheck/lint 并重截图受影响状态。Confidence: 0.75
- Subagent 治理(以 episode-35 实证经验为准):正式制作由主线程完成;subagent 仅在用户明确选择并行开发模式时承接章节或做只读审查,只报告——从不 git commit、不留持久 dev server、不跑 build/audio 工具,自检上限为一次只读 pnpm typecheck,验证链与 commit 集中主线程;制作类交付后主线程重读交付并重跑全链,只读审查类抽查报告所引文件与证据链;交接契约未覆盖的机制级规则仍会复发(ep35:方向化延迟)——复核时按已知机制级规则批量自查;checkpoint 授权边界不因产出质量好而松动;agent 被中断后不从零重做:先盘点其产物并逐文件核验完整性(narrations、CSS、素材),把已完成/缺失/接续点写进重派 prompt(盘点确认无任何产物时在重派 prompt 显式声明从零);批内部分交付时先给用户已完成部分预览(ep05 用户明示“先将已经实现的内容给我预览”):只注册已落盘章、簿记推进与 scoped commit 随行、dev server 验收指针先行交付,缺失章重派转后台与用户走查并行、落盘后再注册+重跑全链+补提交;ep35 并行形态(首章主线程唯一风格锚、每 agent 2 章、prompt 内联消化规格+逐字 beat)已实证可复用;ep05 用户裁决并行模式时明示"请遵从taste中的ep35模式",并明示"至少在第一章处停下"——首章主线程做完即停在验收点、获验收放行后才派发并行,是用户强制的最低停点,不因并行模式预授权而省略。Confidence: 0.9
- 并行派发规模与写盘保险(ep06 实证,修正"每 agent 2 章"配比):单 agent 负载 2 章+必读集过重不可靠——首轮 5 agent×2 章全部在写盘前被截断(4 个精确死于 ~26.7 分钟运行时时长上限,usage 0.53M–1.08M 全花在必读与设计推导,零产物落盘);既定配比改为 **1 章/agent、三波(4+4+3)派发**,波次转后台运行、与主线程复核/注册前波重叠,11 agent 全部成功。减负与保险随派发 prompt 落实:①次级参考文档(如 STATE-MECHANISMS/BOUND-MODE 节选)不列必读,硬规则逐项内联;②明示"开写即落盘"纪律——读完必读立即动笔、推导与落盘交错,长 CSS/TSX 用哨兵分段写入(首段结尾注释哨兵→替换推进→末段移除),禁止在思考里完成整章设计再一次性落盘;③同配方跨波章(如 ch8/ch10 同配方)在后波 prompt 指向前波 sibling 的 TSX 顶部/CSS 头注释只读对齐,防构图克隆。Confidence: 0.85
- Subagent 交接契约:整章交 general subagent 时交接必须完全自包含,一律从交接时已提交工件引用、绝不凭记忆——冲突时已提交工件获胜:向它修实现,correction 记录在 commit/报告,修正契约带入后续章;必读清单:craft/reference docs、theme tokens.css、outline 章节块、已验收 sibling 代码为风格锚;冻结章契约:A-page id/recipe/关系机制、逐拍 narrations 原样复制、屏上文案不得改写、narrations.length 断言;硬规则不在本条枚举,逐项从 craft 文档与 visual-design·courseplay 分包转录进 prompt(文件范围、CSS 前缀、token-only、scene-pad、禁 setTimeout/假数据等);entry.tsx import 了未落盘章文件会让 /play 动态导入整个 entry 失败——立即摘除该章 import+注册恢复可预览,落盘后再注册回去;派发 prompt 固定交付报告契约:文件清单(相对路径)、每章 states 数组、每拍主导动作与动画时长预算、状态门控选择器清单、自检逐项 pass/fail、偏离与疑虑披露;packet 的 exact 项按渲染验收(逐字完整可见),不是源码字符串检查。Confidence: 0.85
- 参考与教训:风格/模式挖掘只用 agent 自产工件,用户明确排除的 episodes 不作参考,用户提供的需求文件是绑定输入属另一类;缺的模式先 grep/read 自产 sibling 沿用而非发明;用户或审查在某章指出的验收缺陷,同轮主动自查后续章节同类模式并先修;必修缺陷跨章传播时先收齐全部审查报告再一次性修完、统一重验(区分"后续步骤填充的预留区"=设计意图 与 永久空区=缺陷)。Confidence: 0.8
- 脚本化验证:派生工件对照冻结输入用一次性脚本逐字对照(空白归一化、PASS/FAIL、mismatch 上下文),脚本进 scratchpad 代替肉眼比对;解析/抽取优先廉价确定性手段(如对枚举标记 grep)而非自然语言启发式,已验证的有损启发式只作交叉校验,绝不当锚点;校验报 FAIL 先归因脚本自身(切分/正则/计数 bug)修正重跑,不据脚本 bug 断言工件有错。Confidence: 0.8
- 被事实纠正后:以最细粒度重读文件重新计数,明确撤回错误结论、降级为可靠性风险、基于修正后事实重新推导建议;先弄清工件的结构惯例再做计数式验证,避免误报。Confidence: 0.8
- 风险试点与方案治理:风险性规则改动用沙盒试点把关(真实冻结输入、隔离 tmp/、实现延后,用证据审计出明确 pass/fail 并分 blocking/non-blocking);契约层改动与下游再生成分开受控,延后范围写成显式 out-of-scope 条目而非静默丢弃;实现前逐条款反向对照实测/试点数据审计方案,分诊必修 bug/真实缺口/澄清并说明各修复是否影响已验证结果;绝不单方面改方案文件——给选项然后等。Confidence: 0.8
- Git 提交纪律:契约/治理改动落单个 scoped conventional commit(均带 Co-authored-by trailer);先查基线(`git branch --show-current && git status --short`)只 stage 明确任务路径;提交信息按影响取舍——行为/契约影响须全五件(背景动机、授权来源、逐文件映射、显式 non-goals、实验/回滚步骤),纯簿记/文字级至少动机+授权来源+逐文件映射;`.commandcode/taste` 学习记录改动一并入库并推送远端,单独 `chore(taste)` commit 与功能提交分开;taste 目录内 agent 主动修改与学习系统自动追加条目再分两笔——先单独入库自动学习条目,再做 agent 的 taste 修改(用户批准);写前重读才发现、与 agent 改动落在同一条目无法分离的追加子句随行入库并在提交信息中显式披露——提交 taste 改动前先比对 HEAD 上 taste 文件状态,判定自动追加/改写是否属未提交增量;用户会委托提交其本人手改的文件(实例:episode-06 口播文本"这个修改是我进行的")——先 diff 定性改动内容,绝不代改,单独 scoped commit,授权来源记"用户本人手改并明示委托提交,agent 未改动文件内容"。Confidence: 0.8
- 中断与暂停汇报:中断/恢复先给状态报告——轻中断(无未落盘写操作、无异常、无流程偏离)用三行短格式(已完成/确切中断点/下一步),有写操作、异常或流程偏离才用全序:已提交完成(含验收状态)→ 中断批次逐项表(状态+确切中断点)→ 明确未做事项 → 恢复后有序待办链 → 当前环境 → 交接提议;绿勾不等于完成,未提交/未审状态随行说明;"暂停任务"硬停按主文件交互条执行(零工具调用);证据化盘点(逐项 implemented vs placeholder、重跑验证链让"全绿"反映现实)只用于用户要求汇报状态或恢复生产前的环境确认("接续 <ep>+已完成阶段+请确认环境":git 基线与无关脏文件、冻结输入可解析且产物↔冻结输入计数一致、验证链结果与缺口待决项),确认磁盘工件完好后从确切步骤继续。Confidence: 0.75
- 流程不符被叫停的处置(区别于"暂停任务"全停):用户以"暂停制作+只允许只读操作"叫停并否定流程本身时,立即冻结一切写操作——含进行到一半的步骤,绝不为"把状态推进到合法"而继续写(冻结与编号裁决列表处置按主文件整体放权条),只读诊断/复盘可以继续;复盘按阶段分组、表格逐步骤细化(不要概要式时间线),每步标注[写]/[写-未完成]、失败尝试根因及授权来源(用户指令/taste 条款/skill 契约/validator 报错/我的自行判断;小结仅按此五类汇总),自行落盘显式标"我的自行判断,未请示"、taste 偏离单独标注,异常与未决项单列,末尾如实披露磁盘与验证链红/绿状态(宁可报红不粉饰);结尾请用户指出不符环节,先只读诊断再等明确放行,不辩解、不按自己理解的流程推进。Confidence: 0.8
- 收官复盘(两种模式,不只失败后才复盘):管线测试收官的耗时复盘——按阶段分述各做了什么,耗时归因到具体摩擦源(协议冷启动、规则阅读配额、同步等审查、基线债挡路、must-fix 修复循环),对比批次间收敛度证明学习成本已摊销,附可执行降本方向(簿记工具化/参考 checklist 化/清基线债/审查异步化)供裁决,不做空泛致歉;经验固化复盘——实证经验与硬边界教训落项目 docs/(先看现有文档风格),组织视角听用户指定并按指定视角整份重写而非原地增补,组织为可复用资产(分段式 subagent 提示词模板、步骤化制作流程、按配方/构图归类的已验证手法),只收实际发生且验证过的经验,构想/推测一律排除或显式标注且不得当作经验陈述。Confidence: 0.7
- 设计与放权治理:没有好答案的设计张力先协作探讨(证据诊断各候选为何失败,锚定 skill 声明的哲学),不急于打补丁;开放设计问题在验证出新设计前不得编码进 contract/taste;放权保持窄、实验性、仅删除性——显式边界清单+显式关闭的未授予权力+恰好一条保守默认附加审查问题+每次行使自我文档化,失败一眼可检出、回滚平凡,试点后再谈扩展。Confidence: 0.85
- 非本会话所为的工作区改动:发现即查 provenance(逐文件 git diff 定性),验证其自带测试,再以 A/B 处置选项交用户 checkpoint 裁决——绝不擅自回滚,也绝不把他人改动混入自己的提交;范围外缺口/基线债仅报告备案交用户裁决,不修、不并入当前 scoped commit,继续当前任务。Confidence: 0.8
- 工具/测试失败隔离复现:先跑配套测试定位失败用例,再在 tmp 沙盒用最小 fixture 复现(临时 cwd、逐项拷输入+theme、execFileSync 抓 stderr),逐输入二分根因——区分"代码坏/数据坏/工作区历史操作坏"并归因到具体提交;沙盒内引仓库工具一律绝对路径。Confidence: 0.6
- TTS 语音合成:音频属逐实例授权项(单次授权不外推为全局默认,不自动加语音);获授权后 `pnpm audio:extract -- --episode <ep>` 提取分段(段数=拍数,封面静默跳过)→ `pnpm audio:synthesize -- --episode <ep> --provider edge --voice <音色>` 合成(音色等参数逐实例指定);合成日志的秒数是耗时不是音频时长——疑时长异常用文件大小/实际工件核验,不按日志秒数判失败。Confidence: 0.75
- Taste 维护实证校验:taste 重构/新增后不假定注入生效——用户会要求用测试词开新会话验证核心条目是否体现(中文回复、先方案后动手、编号列表 checkpoint),分包跟随用领域问题验证(先读分包再作答),不跟随则把关键规则上提主文件。Confidence: 0.7
- Taste 修改先引原文:用户要求更改 taste 中某部分时,先逐字引用现有对应原文(所在文件+条目全文+Confidence)并等用户给出具体改法,再按指令落盘——不凭猜测直接改写条目。Confidence: 0.6
- 复盘对账 taste 的口径(用户明示):核对实际流程与 taste 条目时,定性为"冲突"而非"违反"——两侧皆合法、写明调和方向、逐项交用户裁决,不归咎追责;现行流程是较高优先级基准,从流程出发找张力点;用户会手动直接修改 taste 内容,对账/引用前先重读磁盘现状,不凭会话内旧认知。Confidence: 0.8
- 上下文长度驱动的会话收尾:用户主动监控会话上下文长度,过长时明示不再在会话内继续提修改并转向复盘("当前上下文有些长了,我就不在这继续要求修改了,让我们进行复盘吧")——长会话后期不开辟新工作流,顺势复盘并主动提议起草含环境确认清单的"接续 <ep>"开场 prompt 供用户新会话粘贴续作,运行中后台 agent 去留、dev server 去留、未完事项随收尾编号交裁决。Confidence: 0.7
- 会话开场上下文装载:用户开场直接要求"阅读taste和CLAUDE.md"——响应为一次性批量读完主文件路由的全部分包 + 项目根 CLAUDE.md(不按领域筛),随后逐文件一行简报已读内容并表明就绪、等任务指令;开场装载属预热,不借机推进任务。Confidence: 0.6
