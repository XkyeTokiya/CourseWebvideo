【视频标题】
二级节点 OpenAPI：一次请求包含什么

【开场导入】

想象一个场景。你企业的应用要调用二级节点的一项服务。这个应用该怎么开口？它得先告诉对方，要访问什么、想干什么、自己是谁、数据长什么样。一次请求要把这些都带上，对方才能明白你要什么，再把结果还给你。

那么，一次请求到底是怎么组织的？

【正文讲解】

先认识一下接口本身。二级节点对外提供应用程序接口，英文全称叫 Application Programming Interface，缩写就是大家常说的 API。这个接口是一个可以被系统调用的共同入口，不是一个软件页面。你的应用、不同的系统和平台，都能通过这个标准化的入口，来访问二级节点的功能和服务。

这些接口遵循 HTTP REST 风格。HTTP 是一种网络传输协议，REST 是一套设计接口的约定。在这个约定下，GET、POST、PUT、DELETE 是一组常见的方法。方法表达的是请求的意图，读取资源、提交数据、更新、删除，都可以用不同的方法来表示。不过，某个具体接口到底允许哪些方法，要以这个接口的实际文档为准。看到方法名，不能推断接口里有什么字段，也不能推断业务规则。

那么一次调用里，客户端要明确几件事？一共四件。访问什么资源，也就是请求目标；用什么方法；怎样证明调用者身份，也就是认证；请求数据按什么格式表达。这四件事，分别落在请求的不同位置上。

第一层是 HTTP 方法，它说明这次请求想干什么。第二层是请求目标，它指向要访问的接口位置。第三层是请求头，认证信息和内容解释都放在这一层。第四层是请求数据，是这次调用要携带的业务输入。这里要留意，请求目标、请求数据都是抽象的说法，一次请求真正的完整参数，要以实际接口文档为准。

请求发出去以后，二级节点会按照实际接口的定义，接收这个方法、目标、请求头和请求数据，执行相应的服务，再把文档规定的响应参数或结果送回来。请求和响应就这样共同完成一次交互。目标和方法决定访问哪类资源，请求头提供认证与内容解释，数据主体承载业务输入，响应把服务处理的结果带回调用方。而响应里包含哪些参数，也是由同一份接口文档定义的，不能靠通用想象去补齐。

再说请求头里的两条线。Authorization 这一项携带的是身份认证信息，通用写法是 Bearer，加一个空格，再加 token，这个 token 要从身份接口获取。它回答的问题是，调用者是谁。另一条线是 Content-Type，它说明请求数据的内容类型，一个常见的示例值是 application/json，表示数据按 JSON 这种格式来组织。它回答的问题是，请求主体按什么格式来解释。身份认证和内容解释，是两条不同的职责线，不能混在一起。

还要留意一点，数据在传输和存储的时候，采用 UTF-8 编码。UTF-8 是一种字符编码方式，它能处理更广泛的文字和符号，保证字符能被正确表达。但编码解决的只是字符对不对的问题，它不决定数据模型的属性怎么设计。

有一个关系要特别说清楚。请求头里带着 Token，不等于请求一定成功。Token 需要先获取，它有有效期，过期以后要重新获取。具体有效期多长、认证有什么要求，都以当期接口文档为准。同样的道理，看到 POST，不能推断具体有哪些字段；看到 application/json，不能推断数据模型的全部属性。方法、认证头、内容类型，都不能替代字段和业务结果。

完整讲下来，可以记住一个核对顺序。先确认方法和目标，再核对认证头和内容类型，接着按文档填写请求数据，随后只按文档解释响应。背后还有一个衔接关系：OpenAPI 这套机制，规定的是调用的表达方式；标识数据模型，定义的是业务对象的结构。两者靠实际接口文档衔接起来。OpenAPI 是标准化的调用入口，它不是某一份具体的接口清单，也不是一个固定不变的软件界面。

【本期总结】

回到开头的场景。企业节点的应用要调用二级节点，一次请求就是它开口说话的全部准备。这个准备分成几块，各管各的事：方法和目标决定访问哪里、想干什么，请求头回答调用者是谁、数据怎么解释，数据主体带着业务输入，响应再把结果带回来。共同规律是，这四层各司其职，少了一层，这次对话就说不清楚。核心判断只有一个：不要用方法名、认证头或内容类型去猜接口的字段和业务结果，一层一层核对，比任何直觉都可靠。
