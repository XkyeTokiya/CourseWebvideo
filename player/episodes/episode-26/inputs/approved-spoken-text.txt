想象一个场景。你企业的应用要调用二级节点的一项服务。这个应用该怎么开口？应用要弄清访问什么、用什么方法，并按接口要求提供身份信息；需要提交数据时，还要说明数据格式。接收方才能按约定处理请求并返回结果。

那么，一次请求到底是怎么组织的？

先认识一下接口本身。二级节点对外提供应用程序接口，英文全称叫 Application Programming Interface，缩写就是大家常说的 API。这个接口是一个可以被系统调用的共同入口，不是一个软件页面。你的应用、不同的系统和平台，都能通过这个标准化的入口，来访问二级节点的功能和服务。

这些接口遵循 HTTP REST 风格。HTTP 是一种网络传输协议，REST 是一套设计接口的约定。在这个约定下，GET、POST、PUT、DELETE 是一组常见的方法。方法表达的是请求的意图，读取资源、提交数据、更新、删除，都可以用不同的方法来表示。不过，某个具体接口到底允许哪些方法，要以这个接口的实际文档为准。看到方法名，不能推断接口里有什么字段，也不能推断业务规则。

一次调用要确认几类信息：访问什么资源，也就是请求目标；使用什么方法；接口是否要求认证；如果需要提交数据，格式又是什么。这些信息落在请求的不同位置。

HTTP 方法说明请求意图，请求目标指向接口位置；请求头按接口要求提供认证或内容类型。接口要求提交业务输入时，再带上请求数据。哪些内容必需，要以实际接口文档为准。

请求发出去以后，二级节点按实际接口定义接收方法、目标和请求头；如果接口要求请求数据，也一并处理，再返回文档规定的响应参数或结果。

请求目标指向资源，方法表达操作意图；请求头按要求提供认证或内容类型，请求数据在需要时承载业务输入，响应把处理结果带回调用方。响应具体包含什么，同样要看接口文档，不能凭想象补齐。

再说请求头里的两条线。Authorization 可以携带身份认证信息。在采用 Bearer 的示例中，写法是 Bearer、一个空格，再加 token；这里的 token 从身份接口获取，实际认证要求要以接口文档为准。它回答的是调用者的身份。

另一条线是 Content-Type，它说明请求数据的内容类型。一个常见示例是 application/json，表示请求数据按 JSON 格式组织。身份认证和内容解释是两条不同的职责线。

这套示例接口使用 UTF-8 编码传输和存储文本。UTF-8 负责表示字符，让文字和符号能被正确解释；实际接口采用什么编码，应按它的文档确认。编码不决定数据模型的属性怎么设计。

有一个关系要特别说清楚。请求头里带着 Token，不等于请求一定成功。示例中的 Token 需要先获取，也有有效期，过期以后要重新获取。具体有效期多长、认证有什么要求，都以当期接口文档为准。同样的道理，看到 POST，不能推断具体有哪些字段；看到 application/json，不能推断数据模型的全部属性。方法、认证头、内容类型，都不能替代字段和业务结果。

完整讲下来，可以记住一个核对顺序。先确认方法和目标，再核对认证头和内容类型，需要请求数据时再按文档填写，随后只按文档解释响应。背后还有一个衔接关系：OpenAPI 这套机制，规定的是调用的表达方式；标识数据模型，定义的是业务对象的结构。两者靠实际接口文档衔接起来。OpenAPI 是标准化的调用入口，它不是某一份具体的接口清单，也不是一个固定不变的软件界面。

本期总结，回到开头的场景。企业节点的应用要调用二级节点，一次请求就是它开口说话的全部准备。这个准备分成几块，各管各的事：方法和目标决定访问哪里、想干什么，请求头回答调用者是谁、数据怎么解释，需要时由请求数据承载业务输入，响应再把结果带回来。这些部分各司其职，具体哪些必需，要看实际接口文档。核心判断只有一个：不要用方法名、认证头或内容类型去猜接口的字段和业务结果，一层一层核对，比任何直觉都可靠。
