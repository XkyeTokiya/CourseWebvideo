# 51 集口播润色执行 Skill 设计

> **状态：已废止，禁止继续实现。** 自 2026 年 7 月 29 日起，本设计被 `docs/superpowers/specs/2026-07-29-narration-polish-lightweight-skill-v1-design.md` 取代。本文保留为历史记录；其中的状态机、事务锁、manifest 链、独立人工状态门禁和崩溃恢复协议不再是 V1 要求。

## 一、目的

将《51 集口播稿整体润色设计》转化为可恢复、可校验、不会误改任务包的执行流程，降低 Agent 在长批次处理中遗漏事实、术语、数字、必要限定、视觉锚点或处理状态的风险。

本设计定义目录权限、批次状态、校验、复核和恢复流程；`docs/superpowers/specs/2026-07-28-narration-script-full-polish-design.md` 定义口播内容改写标准。两份文档已自 2026 年 7 月 29 日统一为相同的三目录模型；涉及执行与交付路径时以本设计为准，涉及句子是否可改、应删或必须保留时以 7 月 28 日内容规范为准。

## 二、三类文件的职责

### 1. PPT 制作基线：冻结、只读

路径：

```text
episodes/<module>/episode-XX-...-task-package.md
```

任务包继续作为 PPT、分镜、媒体与制作流程的第一来源。润色 Agent 可以读取任务包以确认事实边界、N 段职责、beat 映射和视觉锚点，但不得修改任务包的任何字符。

发现任务包与原口播、PPT 映射或当前设计存在冲突时，只记录异常并停止当前集，不在本流程中修复任务包。

### 2. 原始口播基线：冻结、只读

路径：

```text
outputs/narration-scripts/<module>/episode-XX-...-narration.md
```

该目录保存从任务包提取出的原始口播基线。执行润色时不得直接修改、重新格式化或覆盖这些文件。

现有 `work/extract_narration.py` 仍可维护原始基线，但执行 Skill 不调用它生成润色成果。

### 3. 润色口播交付物：唯一写入目标

路径：

```text
outputs/narration-scripts-polished/<module>/episode-XX-...-narration.md
```

新目录完整镜像原始口播目录的五个模块和 51 个文件。每个文件首次处理时从原始口播基线逐字复制，再仅修改 `[N001]` 至最后一个 `[Nxxx]` 的 N 正文。

润色完成后，该目录成为录制、字幕和成片口播的唯一文字母版。任务包和原始口播只用于追溯、兼容检查和差异审计，不再反向覆盖润色口播。

## 三、版本控制与不可变基线

为保证逐集差异、恢复和审计能力，应将以下内容纳入 Git 跟踪：

1. `outputs/narration-scripts/` 的 51 份原始口播基线；
2. `outputs/narration-scripts-polished/` 的 51 份润色口播交付物；
3. 批次状态清单和最终校验报告；
4. Skill、验证脚本与测试。

在批次开始前，为任务包和原始口播建立 SHA-256 基线。批次结束时必须证明：

* 任务包全部未变；
* 原始口播全部未变；
* 只有润色目录中的目标 N 正文发生了预期变化。

不得把临时基线只保存在 `C:\tmp`。可恢复状态统一保存在：

```text
work/narration-polish/<run-id>/
```

其中至少包括：

```text
batch-input.json
run-state.json
state-snapshots/
episode-XX-manifest.json
episode-XX-validation.json
batch-report.md
```

## 四、批次输入确认与初始化

任何单集进入处理前，必须完成一次批次级初始化并达到 `BATCH_INITIALIZED`。初始化不得分散到各单集 Preflight 中。

### 1. 确认批次输入身份

生成 `batch-input.json`，列出 51 组任务包和原始口播的规范化路径、文件大小、SHA-256、输入身份模式及确认信息。

输入身份支持两种模式：

* `git`：推荐模式。记录仓库 commit、每个受控输入的 Git blob ID 和工作区一致性；
* `approved-working-tree`：仅当预期输入尚未全部提交时使用。生成完整输入清单后，必须由人工确认该清单就是本批次预期基线，并记录 reviewer、确认时间和清单哈希。

未提交工作区的启动时 SHA-256 只能证明后续未变化，不能单独证明输入正确。缺少 Git 身份或人工确认的输入不得进入批次初始化。

### 2. 一次性建立润色目录

若 `outputs/narration-scripts-polished` 不存在：

1. 在同级临时目录完整镜像 51 份原始口播；
2. 验证五个模块、01–51 集号、路径配对和文件数量；
3. 验证每份副本与原始口播逐字节一致；
4. 通过原子目录重命名发布为正式润色目录。

若润色目录已经存在，必须读取既有 `run-state.json` 和批次身份，不得重新复制或覆盖。目录存在但缺少有效状态时，批次标记为 `RECOVERY_REQUIRED`。

### 3. 初始化持久状态

创建批次 run ID、初始 `run-state.json`、版本化状态快照目录和 51 个 `DISCOVERED` 集合条目。初始化报告必须证明：

* 任务包恰好 51 份且路径唯一；
* 原始口播恰好 51 份且路径唯一；
* 润色副本恰好 51 份且与原始口播逐字节一致；
* 三类文件可以按模块和集号一一配对；
* `batch-input.json` 已获得有效输入身份确认。

完成以上条件后，批次状态才可写为 `BATCH_INITIALIZED`。

## 五、执行单位与状态机

单集是最小读取、改写、校验和复核单位。模块只用于校准表达风格、检查相邻分集边界和汇总报告，不得把 7–13 集合并成一次无检查点的写作任务。

每集依次经过以下状态：

```text
DISCOVERED
→ BASELINED
→ CONTEXT_LOCKED
→ DRAFTED
→ MACHINE_PASS ──人工独立复核通过──→ SEMANTIC_PASS
→ FINAL_PASS
→ DONE
```

机器校验失败时采用可恢复分支：

```text
DRAFTED
→ VALIDATION_FAILED
→ REVISION_REQUIRED
→ DRAFTED
```

默认最多允许 3 个修订循环。格式、段外差异、遗漏词项等可以在不改变知识含义的情况下安全修复的问题进入 `REVISION_REQUIRED`；每次修订后必须重新执行全部机器校验，不得只重跑失败项。

只有以下情况进入 `BLOCKED`：

* 无法安全修复的事实或映射冲突；
* 需要修改只读输入才能继续；
* 输入身份或事务写集失效；
* 达到 3 次修订上限仍未通过；
* 存在事实或边界歧义，需要人工决定但尚无结论。

人工复核尚未确认时，当前集最高只能保持在 `MACHINE_PASS`。语义复核要求修改时进入 `REVISION_REQUIRED`，修订后必须重新经过机器校验和人工复核。

执行中断后，只能从 `run-state.json` 中最后一个已完成门禁继续，不依赖 Agent 对话上下文恢复进度。

## 六、单集保护清单

进入改写前，必须为每个 N 段生成内部保护清单。清单不写回口播稿，但必须保存到该集 manifest。

每个 N 段至少记录：

* `id`：N 编号；
* `role`：开场、定义、解释、案例、清单、总结或交接等教学职责；
* `protected_terms`：必须保留的专业术语；
* `numbers`：数字、年份、周期、范围、单位及其语义归属；
* `qualifiers`：建议、可能、通常、相对、至少、根据规模等必要限定；
* `entities`：案例、机构、角色、产品和标准名称；
* `visual_anchors`：PPT 或动画依赖的关键词、关系、方向和清单项；
* `first_reveals`：必须在本 N 段首次出现的概念；
* `boundary_role`：与上一集、下一集或本集范围的交接职责；
* `risk_level`：普通、较高或高风险；
* `notes`：只能记录无法由上述字段表达的特殊约束。

保护清单建立完成并通过完整性检查后，当前集才可进入 `CONTEXT_LOCKED`。

episode manifest 还必须记录以下执行证据：

* `writer_id`、`writer_type` 和写作时间；
* `revision_count` 与每轮 `transaction_id`；
* `reviewer_id`、`reviewer_type` 和复核时间；
* `review_mode`，最终放行时必须为 `human-independent`；
* 三轮人工复核的逐项结论、相关 N ID 和证据；
* 任何人工豁免的理由与确认人。

## 七、单集事务流程

### 1. Preflight

1. 确认批次状态为 `BATCH_INITIALIZED`；
2. 定位任务包、原始口播和已经初始化的润色输出三个路径；
3. 确认当前三份文件与 `batch-input.json`、初始化报告和当前持久状态一致；
4. 创建唯一 `transaction_id`；
5. 在当前事务开始前，对全部只读输入、51 份润色文件和运行状态文件建立事务快照；
6. 记录本次事务允许写入集合；
7. 保存当前集的正文结构基线并进入 `BASELINED`。

本次事务允许写入集合仅包括：

* 当前集润色文件；
* 当前集 manifest；
* 当前集 validation report；
* `run-state.json` 及其版本化状态快照；
* `batch-report.md`；
* 上述文件在同一目录内用于原子替换的临时文件。

当前事务结束时，将工作区与本次事务开始快照比较。先前已完成或尚未开始的其他 50 份润色文件必须保持不变；允许写入集合之外的文件出现变化时，当前事务不得通过。

### 2. Context Lock

1. 通读任务包与原始口播；
2. 标注每个 N 段职责；
3. 建立术语、数字、限定、实体、视觉锚点和首次揭示清单；
4. 核对相邻分集边界；
5. 将结果写入 episode manifest。

### 3. Draft

1. 只编辑润色目录中的当前文件；
2. 只编辑 N 正文；
3. 逐段依据保护清单改写；
4. 不使用跨文件全局替换；
5. 不用新增知识补足删除审核语言造成的篇幅下降；
6. 保存后立即进入机器校验。

### 4. Machine Validation

机器校验未通过时，先写入 `VALIDATION_FAILED` 报告，再根据失败类型进入 `REVISION_REQUIRED` 或 `BLOCKED`。只有所有硬门禁通过后，才进入 `MACHINE_PASS`。

### 5. Semantic Review

`SEMANTIC_PASS` 必须由独立于 writer 的人工 reviewer 确认。同一个 Agent 或同一身份不得同时作为 writer 和最终 reviewer；独立 Agent 可以提供预审意见，但不能代替人工确认或触发 `SEMANTIC_PASS`。

人工 reviewer 必须重新读取原始口播、润色口播、任务包相关段落和保护清单，不得只阅读 writer 的修改说明。复核分为三轮：

1. 事实与边界；
2. 教学口播；
3. PPT 兼容。

复核至少覆盖：

* 每个 N 段仍承担原教学职责；
* 事实、结论强度、案例归属和因果关系不变；
* PPT 视觉锚点和首次揭示位置仍然有效；
* 审核语言已删除而教学边界未丢失；
* 连续朗读自然，无机械替换腔；
* 上下集边界保持稳定。

每轮必须逐项记录 `PASS`、`FAIL` 或 `WAIVED`、相关 N ID、简短依据、`reviewer_id` 和时间。`WAIVED` 必须包含不会改变知识含义或 PPT 映射的理由。任一项目为 `FAIL` 时进入 `REVISION_REQUIRED`；人工确认记录不存在、身份与 writer 相同或证据不完整时，状态保持 `MACHINE_PASS`。

`update_state.py` 只有在 `reviewer_type=human`、`review_mode=human-independent`、`reviewer_id` 与 `writer_id` 不同、三轮清单完整且没有 `FAIL` 时，才允许从 `MACHINE_PASS` 转为 `SEMANTIC_PASS`。

### 6. Finalize

1. 再次执行机器校验；
2. 验证人工 reviewer 身份和三轮复核证据；
3. 写入单集验证报告；
4. 更新 `run-state.json`；
5. 当前集所有门禁通过后标记为 `FINAL_PASS`，随后原子提交为 `DONE`；
6. 不在本步骤修改任务包或原始口播。

## 八、机器硬门禁

每集至少执行以下检查：

1. **只读源哈希**：任务包和原始口播与批次基线一致；
2. **事务写集**：以当前 `transaction_id` 的开始快照为比较基线，只有该事务明确列出的允许写入集合可以变化；其他 50 份润色文件不得变化；
3. **段外一致**：润色文件 N 正文之前和之后的字符与原始口播完全一致；
4. **N 结构**：编号序列、数量、顺序和段落边界一致；
5. **数字归属**：数字、年份、周期、范围和单位仍在原 N 段；
6. **术语归属**：受保护术语仍在原 N 段，除非 manifest 预先登记允许表达；
7. **必要限定**：影响事实强度的限定没有丢失；
8. **视觉锚点**：清单项、对象、关系和方向仍在对应 N 段；
9. **首次揭示**：受保护概念没有提前或延后出现；
10. **幕后语言**：正文中“教材”为零，并扫描高风险审核表达；
11. **新增信息**：新增数字、年份、百分比、标准名、机构名和产品名时报警；
12. **字符变化**：逐段及整集报告变化率，整集默认以 ±10% 为异常门槛；
13. **状态一致**：没有验证报告的文件不得标记为 `DONE`。

数字、术语或限定存在合理表达变化时，不自动放行。必须在单集 manifest 中记录原表达、新表达、语义等价理由和复核结论。

---

批次初始化和最终批次验收另行检查三类目录各 51 份文件、路径一一对应以及润色目录无额外目标文件。文件数量不是单集 `MACHINE_PASS` 的重复门禁。

## 九、持久化、原子写入与恢复

### 1. 原子写入协议

`run-state.json`、episode manifest、validation report、`batch-input.json` 和批次报告不得直接覆盖写入。每次更新必须：

1. 在目标文件同一目录创建带 `transaction_id` 的临时文件；
2. 写入完整内容并刷新缓冲区；
3. 对文件执行 `fsync`；
4. 重新读取并验证 JSON schema、run ID、revision 和内容哈希；
5. 使用同文件系统的原子替换发布正式文件；
6. 清理已经成功提交的临时文件。

所有状态和证据文件至少包含：

* `schema_version`；
* `run_id`；
* `transaction_id`；
* `revision`；
* `batch_input_hash`；
* `created_at`；
* 自身内容哈希或可验证的规范化内容哈希。

### 2. 状态与报告提交顺序

一次状态推进按以下顺序提交：

1. 原子写入 manifest 或 validation report；
2. 生成新的版本化状态快照 `state-snapshots/run-state.<revision>.json`，其中记录所引用报告的路径和哈希；
3. 验证快照引用的全部证据存在且哈希匹配；
4. 原子替换顶层 `run-state.json`；
5. 根据已提交状态重新生成 `batch-report.md`。

`batch-report.md` 是可重新生成的汇总视图，不作为状态真相来源。不得先推进 `run-state.json`，再补写其依赖的验证报告。

### 3. 中断恢复规则

启动或续跑时执行以下恢复检查：

1. 验证顶层 `run-state.json` 可解析且引用证据全部存在、身份一致、哈希匹配；
2. 若顶层状态无效，按 revision 从高到低扫描版本化状态快照；
3. 选择引用链完整且与 `batch-input.json` 一致的最高有效 revision；
4. 将批次置为 `RECOVERY_REQUIRED`，原子恢复顶层状态指针，并重新生成批次报告；
5. 对高于有效 revision 但未被状态引用的临时文件或孤立报告，只做隔离和记录，不将其视为完成证据；
6. 当前事务从最后一个有效门禁重新执行，不从半写报告推断成功。

若没有任何有效状态快照，批次进入 `BLOCKED`，等待人工决定恢复基线或重新初始化。恢复过程不得修改任务包、原始口播或已经由有效状态确认完成的润色文件。

## 十、Skill 目录设计

Skill 作为项目内能力保存：

```text
.agents/skills/polish-course-narration/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── scripts/
│   ├── init_batch.py
│   ├── preflight.py
│   ├── validate_episode.py
│   ├── validate_batch.py
│   ├── update_state.py
│   └── atomic_io.py
├── references/
│   ├── manifest-schema.md
│   └── review-rubric.md
└── tests/
    ├── fixtures/
    └── test_validators.py
```

不需要 `assets/`。不创建 README、安装指南、变更日志或与执行无关的辅助文档。

### SKILL.md 只保留

* 触发条件；
* 三类目录及读写权限；
* 单集状态机；
* 必须读取的业务设计；
* manifest 建立顺序；
* 机器校验调用方式；
* 语义复核要求；
* `BLOCKED` 停止条件；
* 批次完成条件。

详细字段和复核问题放入 `references/`，确定性逻辑放入 `scripts/`，避免把完整业务设计重复塞进 Skill 上下文。

## 十一、批次编排

### 1. 三集试点

正式批量执行前，先选择三类代表集：

* 一集概念解释课；
* 一集接口、操作或流程课；
* 一集包含标准、数字、建议性限定或产品案例的高风险课。

三集均通过后，检查 manifest 是否遗漏字段、校验是否存在误报、口播风格是否稳定，再冻结执行规则。

### 2. 模块推进

试点完成后按模块顺序推进。每集独立完成全部门禁；模块结束时额外执行：

* 相邻集交接检查；
* 术语一致性检查；
* 固定句式和机械过渡语检查；
* 模块字数与异常统计；
* 模块完成状态检查。

### 3. 并发限制

默认顺序执行。若后续使用多个 Agent，同一写作者一次只处理一集，且相邻分集不得在缺少共同边界清单的情况下并行改写。

---

## 十二、异常处理

出现以下情况时必须将当前集标记为 `BLOCKED`：

* 任务包、原始口播或润色输出路径无法唯一配对；
* 原始口播已在批次开始后发生变化；
* 原始口播基线的 N 编号或正文边界异常；
* 任务包与原始口播存在影响事实或 PPT 映射的冲突；
* 无法判断某句话属于事实限定还是幕后审核语言；
* 无法在保持原 N 段职责和视觉锚点的情况下自然改写；
* 机器校验达到 3 次修订上限仍未通过，或修正会改变知识含义；
* 需要修改任务包、PPT、分镜或其他冻结内容才能继续。

`BLOCKED` 记录必须包括文件、N ID、冲突描述、已检查依据和需要的人工决定。

## 十三、测试与验收

### 脚本测试

验证脚本至少覆盖：

* 正常文件解析；
* N 编号缺失、重复和乱序；
* 段外字符变化；
* 数字跨 N 段移动；
* 受保护术语丢失；
* 必要限定删除；
* 首次揭示提前或延后；
* 任务包或原始口播被修改；
* 无验证报告却标记完成；
* 单集事务开始前后的允许写入集合；
* 可修复失败在 3 次内返回 Draft；
* 人工复核缺失、身份相同或证据不完整时拒绝 `SEMANTIC_PASS`；
* 临时文件写入中断；
* 状态引用缺失或哈希不匹配的报告；
* 从最高有效 revision 恢复并隔离孤立报告；
* Git 输入身份与人工确认输入身份；
* 中断后从状态清单续跑。

### Skill 验收

Skill 完成后必须：

1. 通过技能目录格式校验；
2. 通过全部验证脚本测试；
3. 用三集试点验证执行闭环；
4. 证明任务包和原始口播零变化；
5. 证明所有改动只存在于独立润色目录和运行报告；
6. 证明中断后可从状态文件继续；
7. 证明状态文件半写、报告缺失或引用不一致时可确定性恢复；
8. 证明没有独立人工复核证据时不能越过 `MACHINE_PASS`；
9. 证明任何硬门禁失败都不会被标记为完成。

---

## 十四、非目标

本执行 Skill 不负责：

* 修改任务包；
* 修改原始口播基线；
* 重新生成或修改 PPT；
* 更新事实、政策、标准或案例数据；
* 修改分镜、媒体计划、字幕或时长预算；
* 自动决定存在歧义的事实边界；
* 用全局替换完成口播润色；
* 将机器校验结果替代人工语义复核。
