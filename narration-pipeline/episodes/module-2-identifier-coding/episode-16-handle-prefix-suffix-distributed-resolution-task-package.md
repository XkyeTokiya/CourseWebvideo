## 2. Episode Positioning

- 主解释问题：当对象信息分散存放在不同位置时，一串 Handle 编码怎样既指出“由谁管理这段身份”，又让系统沿这段身份找到对象信息？
- 一句话结论：Handle 用前缀标明企业或组织在分级管理体系中的唯一位置，用后缀区分其内部具体对象，并由独立于域名系统的分布式管理与解析体系把完整标识连接到分布式保存的对象信息。
- 纳入范围：教材所述 Handle 的提出者和体系组成；DONA、MPA 与教材所述中国 MPA 的角色关系；前缀与后缀以 `/` 分隔；一级前缀向子前缀从左向右扩展；后缀可使用本地化标识并由企业内部定义；教材电池示例 `86.100.12/00121336401058520109`；完整标识与分布式数据库中产品信息的访问关系；当前性边界。
- 排除范围：DONA、MPA、中国 MPA 和 `86.` 一级前缀在 2026 年的现行状态；Handle 协议、数据结构、解析请求步骤、缓存、服务端部署、注册接口、权限、证书、收费和故障处理；二维码载体；电池编码字段的具体拆分；真实企业前缀或可注册编码；VAA、OID、Ecode、GS1 的结构与选型；任何学习者练习、测验、评分或任务实施。
- 相邻分集边界：第 15 集负责 VAA 的三层结构，本集不以 VAA 术语解释 Handle；第 17 集负责 OID 的树状命名，本集只讲 Handle 前缀的分级扩展，不把它扩写成 OID 树；第 19 集才回答五种体系如何选；第 20 集才设计前后缀规则。

## 4. Content Type and Narrative Strategy

- 主类型：System mechanism（系统机制）。观众应理解一次“通过身份找到对象信息”的逻辑由哪些对象和关系组成，重点是前缀定位管理范围、后缀区分对象、完整标识连接分布式信息。
- 次类型：Design explanation（设计解释）。只用来阐明组织获配前缀后保留后缀自治的理由，不进入字段、长度、校验位或编码方案设计。
- 本集叙事链：对象信息分散带来查询问题 → Handle 体系的治理与解析定位 → 前缀承担分级管理位置 → 后缀承担内部对象区分 → 用 `/` 拼成完整标识 → 读取教材电池示例 → 完整标识关联分布式信息 → 当前性与实现边界 → 收束机制。
- 问题闭合方式：从“信息不在编码里，为什么编码仍能帮助找到信息”出发，先拆开前缀和后缀的职责，再把完整字符串放回治理与解析关系；最后明确 Handle 提供身份入口，不等于把数据塞进编码，也不等于本集已给出协议实现。

## 6. Continuous Narration Master Script

以下 N001–N014 是本集唯一可录制口播文字来源。后续页面、分镜或制作备注只能引用这些 ID，不得另写第二份讲稿。

[N001]
想象一块工业电池离开工厂以后，还要经历运输、装配、维护和回收。产品规格、生产日期、批次和维修记录不会都写进编码，也可能分散在不同位置。那一串身份符号怎样帮助系统确认“查的是同一块电池”，并进一步找到与它关联的信息？这正是理解 Handle 的入口。

[N002]
教材把 Handle 介绍为一套完整体系：它不仅定义编码规则，还包含独立于互联网域名系统的解析体系，以及全球分布式管理架构。因此，Handle 不能只当作一串带斜杠的字符来背。编码负责标明身份，管理体系负责分配命名空间，解析体系负责把标识与对象信息联系起来。

[N003]
教材还把 Handle 的提出者追溯到罗伯特·卡恩。人物背景不是本集重点，重要的是这套体系从一开始就把编码、管理和解析放在一起考虑。换句话说，先要回答谁有权管理一段前缀，再回答组织内部怎样区分具体对象，最后才谈怎样通过完整标识访问信息。

[N004]
在治理层面，教材称数字对象编码规范机构 DONA 基金会负责 Handle 全球注册及解析服务的运营、管理、维护和协调；其下的全球并联顶级前缀管理机构 MPA，负责分配和管理一级前缀下的子前缀。这里我们只按教材归属理解角色，不把它声称为 2026 年现行安排。

[N005]
教材进一步称，我国三个机构组成的中国 MPA 获得了“86.”一级前缀的管理权。这一机构名单和前缀状态具有动态性，本集没有现行权威版本可供核验。因此，画面必须保留“教材所述”的时间边界，不能把示例前缀当成今天可直接申请或使用的凭据。

[N006]
回到编码结构，Handle 标识由前缀和后缀两部分组成，中间用斜杠分开。前缀是分配给企业或组织的唯一标识，它回答“这段身份由哪个管理范围负责”；后缀由企业内部用来标识具体产品，它回答“在这个组织内部，究竟是哪一个对象”。

[N007]
前缀还具有分级扩展关系。教材说，从一级前缀开始，可以从左向右依次拓展。以教材示例为例，“86”继续扩展为“86.100”，再扩展为“86.100.12”。这帮助我们看见管理位置逐级细化，但不代表所有 Handle 前缀都固定为三层，也不说明各段必须使用固定长度。

[N008]
后缀承担的是本地对象区分。教材说明，后缀可以直接使用本地化标识，通常由企业内部定义，并可关联产品规格、生产批次、生产日期等信息。这里的“关联”很重要：信息不必全部编码进后缀，后缀首先要稳定地区分对象，再由系统把对象与信息连接起来。

[N009]
把两部分拼起来，就得到教材电池示例的完整读法：前缀是“86.100.12”，后缀是“00121336401058520109”，中间用斜杠分隔。完整字符串只用来解释结构。它是教材假设示例，不是某家真实企业的注册前缀，也不是一块真实电池的可查询身份。

[N010]
教材图 2-3 又把前缀细分为国家、行业和企业层级，并把完整编码与二维码放在一起展示。制作时可以借图理解前后缀，但二维码只是载体示意，不能被放大为可扫描入口；国家、行业、企业的标注也只能忠实重绘，不能补成教材没有给出的申请或解析步骤。

[N011]
现在再看“分布式解析”。教材给出的稳定结论是：Handle 系统允许通过完整编码访问保存在分布式数据库中的电池产品信息，例如规格、生产日期、批次号和序列号。我们可以把它理解为：完整标识提供共同查询入口，数据仍可以保存在与业务相适应的位置。

[N012]
但这句话不能被扩写成一条虚构的网络流程。教材没有说明请求先到哪个服务器、经过几个节点、是否使用缓存，也没有给出接口字段、数据库地址和权限规则。因此，本集只画“完整标识关联分布式对象信息”的确定性关系，不画未经支持的服务拓扑或软件界面。

[N013]
理解 Handle，可以沿三个问题检查：前缀属于哪个管理范围，后缀区分哪个内部对象，完整标识关联哪些对象信息。第一问保护命名空间的治理位置，第二问保留企业内部的对象管理能力，第三问让分散信息围绕同一身份被查询。三者缺一，都会把 Handle 误读成普通内部编号。

[N014]
回到开头那块电池，Handle 的机制可以浓缩成一句话：前缀定位组织和管理范围，后缀识别组织内部的具体对象，完整标识再通过分布式解析体系连接对象信息。至于 Handle 与 OID、Ecode、GS1 应该怎样选择，留到后面的比较集；本集先把前后缀和解析关系讲清楚。
