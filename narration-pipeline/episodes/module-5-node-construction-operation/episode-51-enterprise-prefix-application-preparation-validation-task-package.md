## 2. Episode Positioning

- 主解释问题：企业准备申请前缀时，哪些信息需要先整理和相互校验，如何把申请提交给授权的承接方，并在不虚构当前入口的前提下判断流程已经完成？
- 一句话结论：教材将流程归纳为“选择所属承接方或教材列出的服务渠道—准备企业、法人和联系人信息—检查信息与自编码前缀的一致性—提交申请—由平台管理员审核—审核通过后完成前缀申请”；这些是教材流程关系，不是可直接照抄的当前页面或办理承诺。
- 纳入范围：5.2.3“企业前缀申请方式”中所属二级节点/相关服务平台的渠道分层；任务实施“企业前缀申请”中的账号注册前置、企业资质信息准备、单位/法人/联系人三类信息、提交与管理员审核；图 5-4–5-6 的流程语义。
- 排除范围：二维码或小程序真实入口、网址、账号、密码、当前表单字段、证件号、联系方式、前缀字符串示例、审批时限、审核标准、接口、标准版本、IDHub 托管/自建部署、License 申请与安装配置。
- 相邻分集边界：BMS/SNMS/ENMS层级责任属标识数据管理与注册解析模块，本集不展开；第47–48集讲企业节点功能与数据同步，第49集讲IDHub产品架构，第50集比较自建与托管。本集只把申请前的准备和信息校验落到可验证的流程语义，并在模块五主线内完成收束。

## 4. Content Type and Narrative Strategy

- 主类型：Operational demonstration（操作流程演示）。观众需要理解一条可检查的准备—提交—审核流程，但本集不承诺任何当前界面可复现。
- 次类型：System mechanism（系统机制）。用申请方、承接方和管理员的责任关系解释为什么校验必须发生在提交前。
- 叙事链：制造企业准备申请 → 选择已核验授权渠道 → 整理单位/法人/联系人三类信息 → 核对自编码前缀与主体信息 → 提交申请 → 管理员审核 → 以审核通过确认完成 → 回到动态边界。
- 问题闭合方式：开场把“申请前缀”拆成信息准备、相互校验和责任交接三件事，末尾用“审核通过才算完成、入口与字段必须另行核验”同时闭合流程和证据边界。

## 6. Continuous Narration Master Script

以下 N001–N014 为本集唯一可录制口播文字来源。后续分镜只能引用这些 ID，不得另写第二份讲稿。

[N001]
设想一家制造企业准备接入工业互联网标识体系，眼前的任务不是立刻打开某个页面，而是先把申请责任和准备信息理清。企业前缀申请至少要回答三个问题：从哪里进入，准备什么，怎样判断已经完成？

[N002]
教材把流程放在企业节点运营管理中介绍：企业可以向所属二级节点单位申请，也可以通过教材列出的相关服务渠道申请。这里的渠道只说明责任归属和进入方向，不等于今天仍然有效的网址、二维码或产品入口。

[N003]
真正开始申请前，先确认自己使用的是经过授权、并且在当前版本中可核验的承接方。教材任务实施把企业账号注册放在前面，也明确说明教学材料不提供实际操作账号。因此，本集只讲访问前置，不展示账号、密码或任何登录凭据。

[N004]
进入准备阶段，可以把信息按三组整理：单位信息、法人信息和联系人信息。教材页面列出了这些组别下的若干示例类别，但它们是教学材料中的信息组织方式，不是我们可以直接复制的当前表单字段。准备的目标是让主体、责任人和联系路径彼此对应。

[N005]
校验时先看三组信息是否指向同一个申请主体，再看需要提交的证明材料是否来自授权来源、是否清晰可核对，最后确认联系人能够承担后续沟通。教材没有给出当前必填清单、文件大小、认证方式或补件规则，所以这些细节不能由截图推出来。

[N006]
企业自编码前缀也要放回主体信息中一起检查。检查的重点不是背下教材里的示例字符串，而是确认前缀由有权的承接方认可，企业名称、申请主体和前缀归属没有互相矛盾。具体格式和校验规则必须以当期授权说明为准。

[N007]
提交前可以做一次四项核对：申请主体是否一致，三组信息是否完整，材料是否可核验，自编码前缀是否与主体关系一致。这里只保留教材支持的完整性和一致性判断，不增加审批分数、自动校验接口或成功率指标。

[N008]
完成核对后，申请人把信息提交给对应的承接系统。提交动作意味着责任从准备阶段转交给平台管理员，并不意味着前缀已经即时生效；流程图中的“提交”和“审核通过”必须分开呈现。

[N009]
管理员审核企业前缀申请，教材给出的完成条件是信息填写无误并审核通过。这个结论只说明教材流程的责任落点，不提供当前审核时限、人工或自动审核比例，也不承诺任何申请结果。

[N010]
把前面的关系画成一条确定性流程：授权渠道指向信息准备，信息准备进入一致性校验，校验通过后提交，提交再进入管理员审核，最后以审核通过标记申请完成。每个节点都对应教材已读的动作，不能在中间插入截图中没有的接口或状态。

[N011]
图 5-4 到图 5-6 的价值，是帮助我们读懂申请的先后关系，而不是提供一套永远不变的操作界面。二维码、页面标题、按钮位置和字段名称都可能随系统版本变化，因此下游画面只能重绘关系，不能把旧页面当成当前指南。

[N012]
申请完成以后，企业才进入前缀使用和企业节点运营的后续工作。本集不展开托管、自建、IDHub、License 或部署配置；那些内容分别属于前面已经划定的建设模式和产品边界。

[N013]
因此，本集的验证标准很克制：准备信息有来源，三组信息彼此一致，自编码前缀的归属关系说得清，提交和审核两个动作没有混在一起，最终状态只使用“审核通过”这一教材表述。入口、字段、账号、审核时限、接口和标准版本仍需另行取得当期证据。

[N014]
当你能沿着“授权入口—信息准备—一致性校验—提交—管理员审核—审核通过”复述这条链时，就掌握了教材要求的企业前缀申请脉络。记住，流程关系可以稳定复用，具体界面必须先核验再制作；这也是企业节点接入时最重要的证据边界，并为本模块从二级节点建设、持续运营到企业节点接入的主线画上句号。
