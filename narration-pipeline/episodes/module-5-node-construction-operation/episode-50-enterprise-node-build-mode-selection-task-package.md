## 2. Episode Positioning

- 主解释问题：企业已经决定建设企业节点时，怎样根据自身需求和资源条件，在自建与托管之间比较建设路径、资源责任和可见的下一步？
- 一句话结论：自建把企业节点建设放在企业自有资源上，要求带宽、存储、计算面向未来业务并支持弹性扩展；托管把标识解析相关数据和服务托管到二级节点，由企业提交托管申请、经二级管理员审核后使用企业节点标识服务。选择应回到企业资源条件与管理责任，而不能凭空比较价格、SLA 或合规结果。
- 纳入范围：教材 5.2.3“企业节点建设模式”导语；自建模式的自有资源、带宽/存储/计算、未来业务需求、弹性扩展和下载 IDHub 安装包一键部署标识服务；托管模式的数据与服务托管到二级节点、受托部署单位的数据管理义务、托管申请与二级管理员审核、审核后使用标识服务；图 5-3 的两条流程作为语义核对依据。
- 排除范围：IDHub 社区版/标准版能力、版本状态和厂商当前产品能力；下载地址、安装命令、服务器配置、云厂商、成本金额、报价、SLA、可用性、合规认证、数据驻留结论、审批时限、审核标准、代理服务器实现、企业前缀申请字段与界面；任何真实企业案例结果和当前部署规模。
- 相邻分集边界：第 49 集负责 IDHub 产品架构与版本信息，本集只把教材中的“下载 IDHub 安装包”作为自建流程节点，不复述产品能力；第 51 集负责企业前缀申请方式和当期入口，本集只讲模式流程，不演示申请。

## 4. Content Type and Narrative Strategy

- 主类型：Comparison and selection（比较与选择）。观众需要知道两种建设模式分别把资源和流程责任放在哪里，并能读懂教材给出的两条流程。
- 次类型：Construction and operations（建设与运营）。用于说明模式一旦选定，对建设主体、服务承载和持续管理意味着什么，不进入实施命令。
- 本集叙事链：匿名企业的模式选择问题 → 自建资源前提 → 托管服务与审核关系 → 图 5-3 两条三步流程 → 比较维度与证据边界 → 用“可核验条件”收束而非虚构优劣。
- 问题闭合方式：先区分“谁提供资源、谁承载服务、谁承担管理动作”，再把两种流程并列呈现，最后明确只能依据企业实际资源与当期正式要求决策，不能从教材推导价格、SLA、合规或当前产品能力。

## 6. Continuous Narration Master Script

以下 N001–N014 为本集唯一可录制口播文字来源。后续分镜只能引用这些 ID，不得另写第二份讲稿。

[N001]
一家准备接入标识解析服务的制造企业，已经知道企业节点要承担注册、解析、业务和数据管理，但还没有决定由谁来建设和承载这项能力。它面对的不是“哪一个按钮更方便”，而是资源放在哪里、服务由谁承载、日常管理由谁完成。今天我们只比较教材给出的自建模式和托管模式。

[N002]
这里的企业和场景是教学情境，不对应某家真实企业。模式选择要回到两个证据问题：企业是否准备好用于节点的自有资源，是否需要把标识解析相关数据和服务托管到二级节点。教材没有给出价格、服务等级或合规结果，因此这些不能被当成选择结论。

[N003]
先看自建模式。教材把它定义为企业依托自有资源建设企业节点。这里的资源至少包括带宽、存储和计算，而且要满足未来一定时期的业务发展需求，并支持弹性扩展。也就是说，自建首先是资源和持续建设责任的安排，不是简单地把一份安装包放到电脑上。

[N004]
在教材给出的流程里，企业前缀申请之后，企业人员下载 IDHub 安装包，就可以一键部署使用标识服务。随后还要进入系统配置。这里的“可以一键部署”只复述教材流程节点，不提供下载地址、安装命令、服务器规格或当前产品能力，也不把它承诺成任何企业都能直接复现的现行方案。

[N005]
再看托管模式。企业节点可以把标识解析相关数据和服务托管到二级节点。教材同时写明，受托部署单位有义务加强企业节点数据管理，保障企业合法权益。托管改变的是服务承载和管理关系，并不意味着企业可以忽略自己的数据治理责任。

[N006]
托管流程同样从企业前缀申请开始。接着，企业向二级节点提交托管申请，由二级管理员进行托管审核；审核通过后，企业即可使用企业节点标识服务。我们保留“申请、审核、使用”这三个动作，但不补审核时限、申请字段、通过标准或代理服务器怎样实现。

[N007]
把教材图 5-3 放在一起比较，自建的三步是“企业前缀申请、快速部署企业节点、系统配置”；托管的三步是“企业前缀申请、企业托管、使用标识服务”。两条路径都从前缀申请开始，但第二步的责任不同：一条进入企业自己的部署，一条进入面向二级节点的托管关系。

[N008]
因此，可以用四个维度读这张比较图。第一是资源条件：自建依托企业自有资源，托管把相关数据和服务放到二级节点。第二是服务承载：自建在企业侧完成节点部署，托管由受托部署单位承载相关服务。第三是管理动作：自建要面对资源扩展和系统配置，托管要完成申请并等待二级管理员审核。第四是下一步边界：两种模式都不能替我们决定企业前缀申请的当期入口。

[N009]
注意，教材只支持这些关系，不支持一个简单的“自建更强、托管更便宜”结论。我们没有报价、总拥有成本、服务等级协议、可用性数字或合规认证资料，也不能从“保障企业合法权益”推导出具体法律责任分配。比较图应该保留证据边界，而不是用虚构指标制造排名。

[N010]
同样不能把自建资源条件改写成固定容量或性能阈值。“满足未来一定时期”和“支持弹性扩展”是方向性要求；实际的带宽、存储、计算和扩展方案，需要结合企业业务与当期技术要求另行核验。托管也不能被画成一个没有管理边界的黑盒，至少要保留企业申请、二级节点和管理员审核三个角色。

[N011]
如果把两种模式画成责任链，自建侧可以看到企业前缀申请、企业部署、系统配置和后续资源管理；托管侧可以看到企业前缀申请、托管申请、二级管理员审核以及审核后的标识服务使用。两条链都只是教材支持的教学重绘，不是某个产品的操作界面，也不是对当前节点拓扑的证明。

[N012]
回到开场问题，模式选择至少要先核对四件事：企业能否提供并持续维护自有资源，未来业务是否需要弹性扩展，谁承载标识解析数据和服务，以及企业能否按要求完成申请、配置或审核协作。四个问题帮助我们读懂模式差异，但不会自动给出一个脱离场景的唯一答案。

[N013]
下一集会进入企业前缀申请方式，讨论准备什么信息、通过什么当期入口完成校验。本集到这里停止，不预演申请页面，也不把教材图 5-3 的按钮、页签或流程文字当作当前平台界面。涉及产品版本、入口、字段和审批规则时，必须回到制作前实测和正式文档。

[N014]
所以，自建还是托管，不是抽象的优劣排名，而是资源、承载和管理责任的选择。自建对应企业自有资源、未来需求和弹性扩展；托管对应二级节点承载、企业申请和管理员审核。只要保留这些教材边界，并把动态产品与服务信息另行核验，企业节点建设模式才有可解释、可追溯的决策起点。
