## 2. Episode Positioning

- 主解释问题：二级节点不是只部署一套解析软件；它必须管理哪些数据、与哪些角色对接、怎样证明容量和可用性满足建设底线？
- 一句话结论：建设底线可以按“数据可管理且可同步、接口上下贯通、容量和可用性留有冗余、部署资源可扩展”四个问题验收；教材中的阈值属于《工业互联网标识解析二级节点建设导则（2021年）》列出的典型指标，制作前仍需核对适用版本。
- 纳入范围：标识注册数据、标识业务数据、系统运行数据；元数据与元数据库；核心数据托管至国家顶级节点（灾备节点）；向国家顶级节点的申请、同步、监测、应急接管；支持递归解析请求和 VAA、GS1、Handle、OID、Ecode 解析协议；企业节点接入、同步和运行监测；向标识注册管理机构提交责任主体基本信息、所属行业和联系人等必要注册信息；历史解析峰值、1万 QPS、2–3倍带宽冗余、99.99%整体可用性、负载均衡、扩容与自建/委托部署。
- 排除范围：第43集的牵头主体选择和部署责任论证；第45集运营、服务、人员、月度报备和退出机制；第46集基础设施/网络/应用/数据/管理/物理安全六层细则；协议字段、认证头、数据库表、服务器品牌、云厂商、现行标准编号或当前节点数量。
- 相邻分集边界：二级节点的总体职责与功能体系属标识数据管理与注册解析模块的责任范围，本集不展开；第43集解决“谁来建、采用哪种部署模式”；本集解决“技术底线如何验收”；第45集解决“建成后如何持续运营”；第46集解决“如何做专项安全保障”。

## 4. Content Type and Narrative Strategy

- 主类型：Construction and operations（建设与运营）。观众要学会把二级节点建设方案拆成可验收的技术问题，而不是背诵一串指标。
- 次类型：System mechanism（系统机制）。用来串起数据对象、接口角色、请求/同步方向和容量约束。
- 本集叙事链：上线验收情境 → 数据底座 → 上下游接口 → 性能指标的“峰值+冗余+可用性” → 扩容与负载均衡 → 自建/委托部署的资源要求 → 版本与边界提示 → 四问式验收结论。
- 问题闭合方式：先把“能否接入和提供服务”拆为数据、接口、性能、部署四问，再将每问对应到教材条款，最后提醒阈值版本待核验，避免把教学指标当作当前承诺。

## 6. Continuous Narration Master Script

以下 N001–N014 为本集唯一可录制口播文字来源。后续视觉节拍只引用这些 ID，不另写口播。

[N001]
假设一个行业二级节点准备上线，建设团队拿着方案接受验收。最先要问的不是“服务器买了多少”，而是四个技术问题：数据能不能管、接口能不能通、性能能不能撑住、部署能不能扩展。本集沿着这四问，梳理教材对二级节点建设的技术底线。

[N002]
第一问是数据。二级节点应管理标识注册数据、标识业务数据和系统运行数据，并根据所服务行业的特点定义元数据、建立元数据库。企业节点按照这些元数据提供标识对象的属性值，二级节点还要把核心数据托管至国家顶级节点，也就是灾备节点。这里的关键是数据对象和管理责任有边界，而不是把所有业务系统都搬进二级节点。

[N003]
数据管理还必须形成同步关系，保证上下级数据和运行状态保持准确、一致。教材没有给出同步字段、频率或存储表，所以画面只保留“注册、业务、运行”三类数据和同步箭头，不补写接口细节。

[N004]
第二问是向上怎么接。教材列出二级节点对国家顶级节点的四项对接要求：先提交对接申请，再同步标识注册数据、标识业务数据和系统运行数据；同时接受运行监测，必要时由国家顶级节点进行业务应急接管。它们描述的是责任关系和服务连续性，不是某个软件页面的操作步骤。

[N005]
向递归节点的一侧，二级节点要支持递归解析请求，及时响应并返回企业节点信息，还要支持 VAA、GS1、Handle、OID、Ecode 等常见标识体系对应的解析协议。教材没有规定本集要展示哪一种报文或协议版本，因此只画请求、响应和协议族，不虚构字段、认证头或时延数字。

[N006]
向企业节点的一侧，二级节点要支持企业接入，并制定必要的接入管理规范；双方进行数据同步，二级节点还要监测企业节点的服务状态，并按要求向国家顶级节点上报企业节点信息。另一个管理接口面向标识注册管理机构，提交责任主体基本信息、所属行业、联系人等必要注册信息。

[N007]
第三问是性能。教材把它写成几项典型指标：解析能力至少达到节点历史解析峰值的三倍；基本带宽在满足一万 QPS 标识解析的基础上具备二到三倍冗余；系统、存储和网络具备高可用性，整体可用性达到百分之九十九点九九。

[N008]
这些数字要按教材引用的《工业互联网标识解析二级节点建设导则（2021年）》来理解，不能直接当作二〇二六年的统一强制阈值。制作前必须核对适用版本和验收口径。教学上更重要的关系是：用历史峰值估算能力，用带宽冗余抵抗波动，再用系统、存储、网络的整体可用性保护服务连续性。

[N009]
性能还包括可扩展性。教材要求数据库硬盘能够根据注册和解析数量扩容，注册与解析系统支持负载均衡，并可按实际情况扩展网络带宽、服务器计算和数据存储。这里没有给出扩容触发点、集群规模或云产品名称，所以只能表达“监测业务量—保留扩容路径”，不能画成某个厂商的架构图。

[N010]
第四问是部署。二级节点可以自建，也可以委托国家顶级节点运行机构部署。无论采用哪种模式，带宽、存储和计算资源都要满足未来一定时期的业务发展需求，并支持弹性扩展。自建强调责任主体依托自有或租用的云资源建设；委托部署强调由国家顶级节点运行机构提供部署和运行支撑。

[N011]
把四问合在一起，技术验收顺序就是：先确认数据和同步边界，再核对四类接口，接着按适用版本核对容量、冗余、可用性和扩容路径，最后检查部署资源能否支撑未来增长。每一项都要有证据，不能用“系统已经上线”替代。

[N012]
本集有意把安全只留在边界上。核心数据托管、服务连续性和运行监测会与安全相关，但基础设施、网络、应用、数据、管理和物理环境的防护措施属于第四六集；运营制度、服务承诺、人员岗位和月度报备属于第四十五集。

[N013]
因此，技术底线不是组件越多越好，而是每条要求都能回到可复核问题：数据是否管理同步，接口是否覆盖角色，性能是否按适用版本留出冗余，资源是否承诺可扩展。超出教材的字段、协议版本、厂商和指标，都留在待核验清单里。

[N014]
回到上线验收会议，二级节点能否稳定承上启下，取决于四层关系是否同时成立：数据可管理，接口可贯通，性能有余量，部署可扩展。记住教材指标的来源和版本边界，再把每层要求变成证据清单，建设方案才从“能运行”走向“可验收、可持续演进”。
