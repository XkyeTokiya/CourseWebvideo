## 2. Episode Positioning

- 主解释问题：面对同一台工业设备及其相关记录，怎样判断哪些是主数据、哪些是业务数据、哪些是元数据，数据字典又与元数据有什么不同？
- 一句话结论：不要按“数据存在哪个系统”或“看起来是否基础”来分类，而要看它在回答什么问题：主数据回答“核心业务对象是谁”，业务数据回答“围绕对象发生了什么”，元数据回答“这些数据是什么意思、来自哪里、如何关联”，数据字典则在数据库范围内具体规定表、字段、类型等数据元素。
- 纳入范围：工业业务数据的来源、例项、流程关联与用途；工业主数据的核心实体、唯一性、相对稳定性和跨系统共享性；主数据管理的一致性、准确性、可靠性目标；元数据的定义、描述范围、特点与管理作用；数据字典的数据库范围、数据元素定义与维护目的；四类概念在一个匿名设备维护教学情境中的对照。
- 排除范围：工业大数据三类来源、特征和处理链的完整解释；数据共享层级、制度和数据要素政策；主数据治理组织、实施方法和软件产品；元数据平台、数据血缘算法或真实企业目录；标识数据模型、IDO、属性/事件字段设计；OpenAPI、Apifox、数据库建表语句、接口与任何真实个人或企业数据。
- 相邻分集边界：第 21 集负责工业大数据来源、特征、处理和价值，本集只在对照时提及设备信号，不复述其机制；第 23 集负责数据共享，本集只说明主数据可跨系统共享，不展开共享层级与制度；第 25 集负责标识数据模型，本集不把教学情境编成模型、模板或字段清单。
- 合并理由：教材在 3.1.1 中先后定义业务数据、主数据、元数据和数据字典，并专设两组“概念区分”。四个概念只有放在同一对象、同一判断框架中比较，才能避免分别讲解造成重复；合并后仍能在 6–8 分钟内闭合一个清晰的概念边界问题。

### 3.3 事实边界与证据风险

- 受保护术语：工业业务数据、工业主数据、主数据管理、元数据、元数据管理、数据字典、核心业务实体、唯一性、相对稳定性、跨系统共享、强流程关联性、数据元素、数据类型、业务规则、数据来源。
- 受保护关系：主数据围绕核心业务实体；业务数据由业务运转产生并直接支持执行与决策；元数据描述数据含义、结构、来源和上下文；数据字典聚焦数据库中的表、字段、类型等数据元素。
- 可压缩内容：教材的人口、图书、发动机、电池等多组元数据例子压缩为一个匿名设备情境；图 3-2、表 3-3 和表 3-4 只保留概念作用，不复用其具体结构或值。
- 禁止跨章扩展：工业大数据处理链、共享制度、数据要素政策、主数据治理实施、数据目录平台、数据血缘算法、标识对象模型、元数据模板字段、数据库建表、接口、Token 与 Apifox。
- 教材口径风险：教材将温度、湿度等列入主数据例项，同时在前文将温湿度列入设备作业数据。为避免同一内容跨类别冲突，本集不使用温湿度作为主数据例子，只采用教材定义一致的设备 ID、物料、供应商等核心实体基准信息。
- 隐私风险：教材表 3-4 含姓名、电话号码、地址、订单号和金额的示例值。本集不复用、不展示这些值，媒体也禁止生成可读个人或交易信息。
- 补充来源用途：无。本集未引入教材外标准、政策、产品能力、当前状态或企业案例。
- 动态核验状态：`not applicable`。本集只讲稳定概念，不含需更新至 2026 年的政策、标准、规模、接口或软件界面。
- 未解决缺口：教材没有给出四概念适用于所有企业的数据分类规则，也未说明元数据与数据字典的形式化集合关系。因此本集只提供来源支持的判断维度，不声称它是通用标准或自动分类算法。

## 4. Content Type and Narrative Strategy

- 主类型：Concept boundary。观众需要能够区分四个相邻概念及其边界，重点是消除“看起来都是字段和记录”的歧义。
- 次类型：Comparison and selection。只承担按“描述对象、变化方式、使用目的、作用范围”四个维度进行比较，不要求观众完成分类练习。
- 本集叙事链：一张维修记录为何出现四个名词 → 先看数据在回答什么 → 业务数据 → 主数据 → 二者对照 → 元数据 → 元数据管理 → 数据字典 → 元数据与数据字典对照 → 同一设备四层归位 → 常见误判边界 → 管理价值 → 结论与后续边界。
- 问题闭合方式：始终围绕同一台匿名设备，不换成四组互不相关的例子；每引入一个概念就补上它回答的问题，最后用四层关系图同时保留对象、事件、说明和数据库规范，避免把概念压成四个孤立定义。

## 6. Continuous Narration Master Script

以下 N001–N014 是本集唯一可录制口播文字来源。任何下游页面、字幕或讲者备注只能引用这些 ID，不得另写第二份口播。

[N001]
一台设备完成检修后，系统里可能同时出现设备编号、设备名称、维修工单、故障描述、字段名称和字段类型。它们都与这次维修有关，却不能都叫同一种数据。这个匿名教学情境提出了本集的问题：面对同一对象和同一张记录，主数据、业务数据、元数据与数据字典到底怎样划清边界？

[N002]
区分它们，不能只看数据存在哪个系统，也不能只看它是不是一行表格。更有效的办法，是先问它在回答什么：是在确认核心业务对象是谁，记录围绕对象发生了什么，说明这些数据是什么意思，还是规定数据库字段应当怎样定义？四个问题，对应四种不同角色。

[N003]
先看业务数据。教材把工业业务数据定义为支撑企业核心业务运营的结构化数据，它产生于研发、生产、供应链等环节，例如订单、物料清单和质检记录。业务数据与流程紧密关联，通常随着业务推进不断产生和变化，直接用于业务执行与管理决策。

[N004]
再看主数据。工业主数据描述企业的核心业务实体，是高价值的基准数据。教材列举物料编码、设备 ID、供应商信息，以及客户、产品、员工等对象。它的关键特征是唯一识别、相对稳定，并能跨部门、跨系统共享。这里的稳定是相对的，不等于永远不更新。

[N005]
把两者放回同一台设备就清楚了：设备的唯一编码和基础属性用于确认“它是谁”，属于主数据；围绕设备产生的维修工单用于记录“发生了什么”，属于业务数据。教材还把设备振动信号归入工业大数据。可见，分类看的是数据角色，不是因为它们都出现在设备系统里就合并成一类。

[N006]
第三个概念是元数据。元数据常被概括为“关于数据的数据”，它不以某一条维修记录为中心，而是说明数据本身的含义和上下文。教材列出的描述范围包括名称、类型、所属业务域、取值范围、数据之间的关系、业务规则和数据来源。

[N007]
因此，元数据回答的是“这项数据该怎样理解和寻找”。它具有描述性、共享性、结构化、动态性和多样性。对元数据进行创建、存储、整合和控制，可以帮助使用者理解数据含义，明确上下游关系，并更准确地定位需要的数据。这里不等于某个元数据平台已经自动完成全部分析。

[N008]
第四个概念是数据字典。教材把它放在数据库范围内：它是关于表、字段、数据类型等数据元素的集合，为这些元素提供详细定义和描述，服务数据库的一致性、完整性、设计与维护。也就是说，它更接近一套可查阅的字段规范。

[N009]
元数据和数据字典都会出现字段名称、类型或说明，所以很容易混淆。教材给出的边界是：元数据面向更广泛的数据领域，还关心业务域、来源、关系和规则；数据字典聚焦数据库结构和数据元素。数据字典可以承载一部分具体的描述信息，但不能因此把全部元数据都缩成一张字段表。

[N010]
现在把四个问题并排看。主数据回答“对象是谁”，业务数据回答“对象经历了什么”，元数据回答“相关数据是什么意思、从哪里来、怎样关联”，数据字典回答“数据库中的表和字段怎样定义”。它们不是四个互相替代的仓库，而是观察工业数据的四种职责。

[N011]
在匿名设备维护情境中，可以把设备身份作为主数据，把维修工单作为业务数据；把对工单字段含义、来源和业务关系的说明作为元数据；再用数据字典规定数据库字段的名称、类型和约束。这个情境只用于解释角色，不填写设备编号、人员、时间、金额或任何企业真实值。

[N012]
由此也能排除三种常见误判。第一，存在基础表里的数据不一定都是主数据，关键要看它是否描述核心实体并被共享。第二，主数据相对稳定，不等于静止不变。第三，数据字典不是元数据的全部，它只聚焦数据库领域。字段长得相似，职责和范围仍可能不同。

[N013]
为什么要分清这些角色？教材指出，主数据管理要保障一致性、准确性和可靠性，使不同业务系统能围绕同一核心对象协同；元数据管理帮助理解含义、定位数据和明确上下游关系；数据字典则为数据库设计和维护提供具体依据。概念边界清楚，后续共享和建模才不会从含混的口径开始。

[N014]
所以，判断一项工业数据时，先别急着看它在哪张表里。先问四件事：它是在确认对象、记录事件、描述数据，还是规范字段。主数据、业务数据、元数据和数据字典由此各归其位。下一集再讨论这些数据怎样跨越产线、工厂和产业链共享；标识数据模型则留到后续课程展开。
