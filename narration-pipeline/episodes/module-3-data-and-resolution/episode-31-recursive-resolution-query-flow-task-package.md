## 2. Episode Positioning

- 主解释问题：应用系统只提交一个标识查询请求，递归解析服务怎样代表客户端逐级找到企业解析系统，并把企业应用数据带回，同时利用缓存减少不必要的重复查询？
- 一句话结论：递归节点把客户端从复杂的逐级查询中解放出来；缓存未提供结果时，它依据上一级返回的地址信息依次访问国家顶级、二级和企业解析系统，取得企业应用数据后再返回客户端并缓存请求结果。
- 纳入范围：教材对标识递归解析的定义；递归节点的关键入口角色；本地缓存优先检查；缓存未命中后按应答路径查询；应用系统、解析客户端、递归解析服务系统、国家顶级解析服务节点系统、标识二级解析服务节点、企业解析系统之间的八步请求与返回；企业信息系统、工业互联网平台、工业互联网 APP 等查询触发形式；递归机制对客户端复杂度、解析效率和响应速度的作用。
- 排除范围：标识注册和前缀申请；BMS、SNMS、ENMS 的注册责任链；当前国家顶级、二级、企业或递归节点的数量、城市、部署位置与产品拓扑；接口地址、端口、字段、报文结构、认证、Token、返回码、TTL、缓存淘汰/失效/一致性策略；Handle 或 DNS 的协议细节与当前适用范围；企业应用数据的数据模型；软件界面和可复现操作。
- 相邻分集边界：第 30 集负责“前缀由谁申请、审核、分配和管理”，本集只负责“查询请求怎样逐级到达企业数据”；第 32 集负责把编码、注册、请求、解析、返回组成完整业务闭环，本集不重复编码与注册。

## 4. Content Type and Narrative Strategy

- 主类型：System mechanism（系统机制）。观众应理解“一个请求怎样沿多个解析角色逐级前进并返回”，重点是角色、请求/地址/数据的区别和缓存分叉。
- 次类型：无。本集不要求观众复现接口操作，也不设计递归系统或缓存实现。
- 本集叙事链：应用提出查询 → 递归解析定义与角色 → 先查缓存 → 缓存未命中 → 客户端到递归节点 → 顶级返回二级地址 → 二级返回企业地址 → 企业返回应用数据 → 递归节点回传并缓存 → 多入口与机制价值 → 版本边界。
- 问题闭合方式：先把客户端的诉求限定为“提交标识、获得结果”，再区分逐级返回的两次地址信息与最后返回的企业应用数据；以八步闭合去程和回程，最后回到递归节点替客户端承担复杂查询的价值，并明确教材流程不等于当前部署说明书。

## 6. Continuous Narration Master Script

以下 N001–N014 为本集唯一可录制口播文字来源。任何后续页面、分镜或备注只能引用这些 ID，不得另写第二份讲稿。

[N001]
设想一名设备维护人员在企业应用中输入某台设备的标识，希望查到与它关联的信息。对使用者来说，动作只有提交标识、等待结果；但数据并不一定就在眼前这个应用里。请求究竟该先去哪里、下一站又由谁告诉它，这就是递归解析要解决的问题。这个情境只用于理解机制，不代表某个真实企业的当前系统。

[N002]
教材把工业互联网标识递归解析定义为：在标识解析体系中，通过递归节点完成标识的查询和解析，把标识编码解析为具体网络地址或相关信息，从而支持对物理实体和数字对象的定位与信息查询。这里的关键不是“递归”这个词，而是客户端把复杂查询交给了一个统一入口。

[N003]
这个入口就是递归节点。教材称它为关键性入口设施，并强调缓存的作用。递归节点收到请求后，先查看本地缓存有没有查询结果；如果已有可用结果，就不必再次展开后续逐级查询。教材没有给出缓存有效期、失效、淘汰或一致性规则，所以本集只保留“先查缓存”这一层机制。

[N004]
如果缓存没有结果，递归节点才沿解析服务器返回的应答路径继续查询。教材图三点二五中的核心角色，是解析客户端、递归解析服务系统、国家顶级解析服务节点系统、标识二级解析服务节点和企业解析系统。接下来只按教材八步看清请求和返回，不把这张关系图当成当前部署拓扑。

[N005]
第一步，应用系统通过解析客户端，向递归解析服务系统发起标识查询请求。到这里，客户端只需要把查询交给递归入口，不需要自己掌握后面每一级解析系统的地址。

[N006]
第二步，递归解析服务系统分析客户端请求，再向国家顶级解析服务节点系统发起标识解析查询。教材在这一步记载了 Handle 或 DNS 协议查询，但没有给出适用版本，因此这里只说明教材流程，不把协议名称外推为当前所有部署的统一做法。

[N007]
第三步，国家顶级解析服务节点系统返回的不是企业应用数据，而是标识二级解析服务节点的地址信息。这是理解整条路径的第一个关键：上一级先告诉递归系统“下一站在哪里”。

[N008]
第四步，递归解析服务系统根据刚得到的地址，继续向标识二级解析服务节点发起查询。客户端仍在等待，逐级查找的工作由递归系统代表它继续完成。

[N009]
第五步，二级解析服务节点把结果返回给查询请求方，递归解析服务系统由此获得该标识对应的企业解析系统地址。这里再次返回的是下一站地址，而不是最终的企业应用数据。

[N010]
第六步，递归解析系统向这个企业解析系统地址发起标识查询请求。经过顶级和二级两次地址指引，请求终于到达能够提供该标识关联信息的企业解析系统。

[N011]
第七步，企业解析系统收到请求后，把企业应用数据返回。教材没有给出这些数据的字段、权限、格式或存储位置，因此我们只确认“企业解析系统返回企业应用数据”，不补写任何接口实现。

[N012]
第八步，递归解析服务系统把取得的企业应用数据返回解析客户端，客户端再把结果交给发起查询的应用。到这里，去程由客户端到递归、再到顶级、二级和企业；回程则把地址指引和最终数据逐段带回。教材前文还说明，请求结果会被缓存，为后续查询减少不必要的重复路径。

[N013]
所以，递归解析的价值可以从两个角度理解。对客户端，它不必自行组织复杂的逐级查询；对整个服务过程，缓存和应答路径有助于提高解析效率与响应速度。查询的触发形式也可以不同，教材举出企业信息系统、工业互联网平台、工业互联网应用等入口，但无论入口怎样变化，都不改变递归节点代表客户端完成查询的主线。

[N014]
回到开头的设备查询，真正需要记住的不是八个编号本身，而是三类返回：顶级节点给出二级地址，二级节点给出企业解析系统地址，企业解析系统才给出企业应用数据；递归节点把结果带回客户端，并按教材机制缓存请求结果。这解释了“一次查询怎样逐级找到企业数据”。下一集会把它放回编码、注册与应用返回的完整业务闭环，本集到查询路径为止。
