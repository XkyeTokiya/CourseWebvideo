## 2. Episode Positioning

- 主解释问题：前缀申请不是一个孤立的“填表动作”，三级业务管理系统如何分工，才能让二级节点获得上级资源、企业获得下级前缀，并让注册数据和指向关系落到正确的责任边界？

## 4. Content Type and Narrative Strategy

- 主类型：System mechanism（系统机制）。观众需要理解申请链中三个业务管理系统如何传递责任，而不是记忆一个网页操作步骤。
- 次类型：Process explanation（流程解释）。用上行资源申请、审核分配、下行企业申请和托管/自建分支形成可视化过程，但不把流程重写成当前办理指南。
- 本集叙事链：企业对象准备接入 → 先分清二级节点向上申请 → BMS 审核并分配二级前缀 → SNMS 向下承接企业申请 → ENMS 发起申请 → SNMS 审核并赋予三级前缀 → 托管/自建决定数据管理责任 → 回到版本和现状边界。
- 问题闭合方式：开场提出“谁向谁申请”的混淆，随后按上行、下行和分支三次揭示，最后用责任对照说明“前缀获得”与“标识数据管理”不是同一职责，并明确不提供当前入口或操作承诺。

## 6. Continuous Narration Master Script

以下 N001–N014 为本集唯一可录制口播文字来源。后续分镜只能引用这些 ID，不得另写第二份讲稿。

[N001]
设想一家企业准备把一批新产品接入工业互联网标识体系。问题看似是“申请一个前缀”，实际要先回答三件事：谁向谁申请，谁负责审核，拿到前缀以后谁管理标识数据？

[N002]
教材用三级业务管理系统说明这条责任链：国家顶级节点业务管理系统简称 BMS，二级节点业务管理系统简称 SNMS，企业节点业务管理系统简称 ENMS。它们不是三个并列的网页，而是分层承担申请、审核、分配和企业接入职责的管理边界。

[N003]
先看上行方向。SNMS 向 BMS 提交二级节点申请，同时处理与国家顶级节点的前缀解析配置、企业标识前缀申请分配和数据备案等事项。这里的重点是二级节点把自己的服务范围接入上层体系，而不是某个企业直接跳过二级节点去申请。

[N004]
BMS 的职责是审核申请，并向二级节点分配二级节点标识前缀。教材支持的是“审核加分配”这两个责任动作，没有给出当前的审批时限、材料清单或自动化规则，所以这些内容不能从流程图中补出来。

[N005]
拿到上级前缀后，链条转向企业一侧。企业节点业务管理系统 ENMS 向 SNMS 申请标识前缀；SNMS 完成企业标识前缀审核后，再向企业赋予标识三级前缀。也就是说，企业申请和二级节点向上申请是两段不同的关系。

[N006]
图三点二三把 BMS、SNMS 和 ENMS 画成两两交互关系。教学上应把它读成“上级审核分配、下级提交申请”的责任图，而不是一张可以直接复现的接口时序图。图中没有字段、地址和令牌，这些也不属于本集的事实范围。

[N007]
为什么要把申请和分配拆成层级？因为前缀不仅是一个字符串，还代表谁可以在某个范围内继续组织标识。BMS 把二级范围交给 SNMS，SNMS 再把企业范围交给 ENMS 对应的企业节点；每一层都保留自己的审核和管理责任。这样既能说明资源从哪里获得，也能说明下一级前缀由谁分配，而不是把所有注册动作压到同一个系统里。

[N008]
企业获得前缀后，教材给出两条注册途径：选择二级节点托管服务，或者选择自建企业节点。两条路径都从企业申请开始，但后续谁管理企业标识数据，并不是同一个答案。

[N009]
如果选择二级节点托管，企业的标识注册和相关数据管理可以由二级节点提供的托管能力承接。企业仍然是标识对象和业务数据的责任主体，托管只是教材描述的一种系统承载路径。这里不把它扩展成某个当前产品、合同条款、数据中心位置或服务等级。

[N010]
如果选择自建企业节点，教材明确限定：SNMS 不能做企业标识的数据管理，只能进行标识前缀分配和指向配置。换句话说，前缀仍由上级关系分配，企业标识数据则由企业自己的节点承担管理。指向配置让上级体系知道到哪里继续查找，但这不等于上级系统接管企业数据。

[N011]
因此，图三点二四的分支不是“一个更简单、一个更高级”的产品比较，而是数据管理责任的不同落点。前缀分配和指向配置属于 SNMS 的边界，企业标识数据管理是否由 SNMS 承担，要看企业选择的路径。

[N012]
把整条机制压缩成一行：SNMS 向 BMS 申请并接受二级前缀，ENMS 向 SNMS 申请并获得企业三级前缀，随后按托管或自建路径确定数据管理责任。角色先于界面。这里讲的是教材的角色关系，不是当前办理指南。

[N013]
所以，看到教材中的“在线工具”“注册页面”或接口示例时，要先把它们当作任务实施材料，而不是今天仍然有效的入口。网址、IP、字段、账号和令牌都可能随版本变化，本集不复述，也不虚构新的申请界面。没有当期权威证据时，宁可保留流程占位，也不能补写入口和字段。

[N014]
有了这条责任链，后续的递归解析才有明确的注册基础：先知道前缀由谁申请、由谁审核、由谁分配，再去理解查询请求怎样逐级找到企业数据。申请链解决资源和责任的归属，解析链解决查询怎样到达数据，两者前后相接但不能混为同一流程。下一集会转向递归查询，本集只留下一个判断标准：前缀获得和数据管理，必须放在正确的系统边界内。
