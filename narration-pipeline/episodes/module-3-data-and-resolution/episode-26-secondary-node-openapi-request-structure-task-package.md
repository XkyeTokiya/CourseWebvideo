## 2. Episode Positioning

- 主解释问题：当企业节点要调用二级节点服务时，OpenAPI 请求如何把资源目标、HTTP 方法、认证头、内容类型和请求数据组织起来，又如何接收响应？
- 一句话结论：OpenAPI 把二级节点服务表达为可查阅的 HTTP REST 风格接口；客户端按实际文档确定方法、目标、请求头和参数，服务端返回文档规定的响应，认证头只证明调用身份，不能凭方法名或示例 Token 推断接口字段和业务结果。
- 纳入范围：二级节点 OpenAPI 的定义和服务对象；HTTP REST 风格；GET、POST、PUT、DELETE 作为资源访问与操作的方法集合；UTF-8 传输与存储的教材说明；请求的抽象组成（方法、目标、请求头、请求数据）；Authorization 的 Bearer 认证头；Content-Type 为 `application/json` 的教材通用说明；请求与响应的往返关系；“完整接口清单、请求参数和响应参数以实际文档为准”的边界。
- 排除范围：任何真实二级节点公网 IP、端口、路径、Token 字符串、账号、企业参数、对象属性字段、响应字段、状态码数值、权限策略、TLS 部署、数据库、代码、Apifox 页面、扫码登录、发送按钮和实操步骤；第 27 集的工具操作；第 28–32 集节点注册、递归解析和节点内部组件。
- 相邻分集边界：第 25 集负责数据模型的对象、属性、事件和元数据；本集负责接口请求/响应机制；第 27 集负责在授权测试环境中的 Apifox 操作；第 28 集以后负责二级节点组件、注册与解析路径。本集不把 OpenAPI 讲成节点部署教程，也不把接口图改写成完整时序。

## 4. Content Type and Narrative Strategy

- 主类型：System mechanism（系统机制）。观众要理解一次调用中“方法、目标、头部、数据、响应”的职责关系，以及二级节点 OpenAPI 为什么能让托管企业节点集成服务。
- 次类型：Concept boundary（概念边界）。用于划清“结构图可以解释什么”和“实际接口文档才能确定什么”，避免把教材示例误当成可复用接口。
- 本集叙事链：企业节点需要调用服务 → OpenAPI 给出标准化入口 → REST 方法表达资源访问/操作 → 请求由方法、目标、头部和文档规定的数据组成 → Authorization 与 Content-Type 分工 → 服务处理后返回文档规定的响应 → 方法/头部不能替代模型字段，实际参数必须查文档 → 为 Apifox 操作建立安全边界。
- 问题闭合方式：先把“请求到底带什么”从抽象疑问变成一个可观察的数据路径，再把每个组成部分的职责分开；最后明确哪些是教材稳定机制、哪些必须以当期文档为准，使观众能理解下一集操作而不提前复制不可用示例。

## 6. Continuous Narration Master Script

以下 N001–N014 为本集唯一可录制口播文字来源。任何后续页面、分镜或备注只能引用这些 ID，不得另写第二份讲稿。

[N001]
假设一个托管企业节点的应用要调用二级节点服务。它不能只把“某个数据模型”直接丢过去，还要明确访问什么资源、用什么方法、怎样证明调用者身份，以及请求数据按什么格式表达。问题是：一次 OpenAPI 请求，究竟由哪些部分组成？

[N002]
教材把二级节点 OpenAPI 定义为二级节点对外提供的应用程序接口，也就是 Application Programming Interface，简称 API。它主要服务托管企业节点用户，让不同系统和平台能够通过标准化接口访问二级节点的功能和服务。这里的重点不是某个软件页面，而是一个可被系统调用的共同入口。

[N003]
这类接口遵循 HTTP REST 风格，用 GET、POST、PUT、DELETE 等方法访问和操作资源。可以把方法先理解成请求意图的表达方式：读取、提交、更新或删除都可能使用不同方法，但某个具体接口到底允许哪种方法，仍要以它的实际文档为准，不能只凭方法名猜业务规则。

[N004]
所以，方法集合解决的是“怎样发出操作意图”，不是“接口里有哪些字段”。教材还说明，数据在传输和存储时采用 UTF-8 编码，目的是让接口能够处理更广泛的文字和符号。编码规则保证字符能被正确表达，却不会自动替我们设计对象属性。

[N005]
把一次请求画成结构图，可以先保留四层：第一层是 HTTP 方法，第二层是请求目标，第三层是请求头，第四层是文档规定的请求数据。这里的“请求目标”只表示要访问的接口位置，“请求数据”是抽象占位；教材明确要求，完整的请求参数要回到实际文档，不能在教学图里凭空添加字段。

[N006]
请求头里至少要区分两种不同职责。Authorization 用来携带身份认证信息，教材给出的通用格式是 Bearer 加一个空格，再接由身份接口获得的 token。画面只能标出这种结构，不能展示真实 Token，也不能把示例字符串当成可用凭证。

[N007]
另一个常见头部是 Content-Type。教材表 3-6 将它列为必填参数，示例值是 application/json，用来说明请求数据的内容类型。它回答的是“主体按什么格式解释”，不是“调用者是谁”；身份认证和内容解释是两条不同的线。

[N008]
请求发出后，二级节点先依据实际接口定义接收方法、目标、头部和请求数据，再执行相应服务，最后返回文档规定的响应参数或结果。教学图到这里就应该停在“响应”这一层，不写入未经核验的字段、状态码、错误文本或业务数值。

[N009]
请求和响应不是两张互不相干的表。请求中的目标和方法决定要访问哪类资源，头部提供认证与内容解释，数据主体承载本次业务输入；响应则把服务处理后的结果带回调用方。至于结果包含哪些参数，必须由同一份接口文档定义，不能用通用想象补齐。

[N010]
这也解释了为什么“有 Authorization”不等于“请求一定成功”。Token 可能需要从身份接口获取，也可能因版本或环境变化而失效。教材称 Token 通常有效期为两小时，但教材没有标明当期服务版本；因此这里只保留“需要按文档管理有效期”的边界，不把两小时当成当前系统承诺。

[N011]
同样，看到 POST 也不能直接推断请求一定包含哪些字段，看到 application/json 也不能推断数据模型的全部属性。OpenAPI 机制负责规定调用的表达方式，标识数据模型负责定义业务对象的结构，两者要通过实际接口文档衔接，而不是由一张概念图替代。

[N012]
如果把关系压缩成一句话，就是：客户端按文档组装方法、目标、请求头和请求数据；二级节点按接口定义处理；服务端返回文档规定的响应。任何缺失的字段、认证要求或错误处理，都应回到授权环境中的当期文档确认，不能靠教材示例地址或网络搜索结果猜测。

[N013]
到这里，OpenAPI 的机制边界就清楚了：它提供跨系统调用二级节点服务的标准化入口，HTTP 方法表达访问和操作，认证头证明身份，内容类型说明数据如何解释，请求与响应共同完成一次交互。它不等于某个具体接口清单，也不等于一个固定不变的软件界面。

[N014]
下一集才进入 Apifox 的调试流程，而且必须使用授权的测试环境和当期接口文档。本集只留下一个可复用的检查框架：先确认方法和目标，再核对认证头与内容类型，随后按照文档填写请求数据，最后只按文档解释响应。这样，理解机制和执行操作才能各自保持准确。
