## 2. Episode Positioning

- 主解释问题：一个物理或虚拟对象怎样被描述成可识别、可寻址、可共享的数字对象？标识编码、解析记录、对象数据，以及属性数据和事件数据之间是什么关系？
- 一句话结论：标识数据模型不是把字段堆在一起，而是先用标识编码确认对象身份，用解析记录找到网络位置，再用对象数据描述对象；其中属性数据刻画对象的固有特征、主体与位置，事件数据记录对象在生产、流通和使用中的行为与变化。
- 纳入范围：数字对象（DO）与可识别数字对象（IDO）的定义；IDO 的标识编码、解析记录、对象数据三要素；标识数据模型（IDM）对现实特征的模拟和抽象；属性数据的对象/基本、主体、位置三类；事件数据的对象、聚合、交易、转化四类；教材任务中的发动机属性清单与元数据定义维度；从对象到模型的来源驱动组织流程。
- 排除范围：编码体系和前后缀规则；工业大数据、主数据、元数据与数据字典的完整重讲；二级节点、节点注册、OpenAPI、HTTP 方法、认证头、Token、Apifox、软件界面、接口字段和请求示例；任何真实企业项目、当前政策/标准状态、学习者练习或测验。
- 相邻分集边界：第 22 集负责四类工业数据的概念边界，本集只回收“对象/事件/描述”的已有判断；第 23–24 集负责共享与数据要素，本集不讨论制度或政策；第 26–27 集负责接口机制与工具操作，本集不把模型讲成 API 请求。
- 隔离理由：3.1.3 将模型概念、属性/事件分类和任务实施中的属性/元数据定义放在同一任务中，但工具操作属于另一个可复现问题；将概念与设计逻辑独立成一集，能在 6–8 分钟内闭合“如何建模”，同时给后续接口集留下清晰边界。

## 4. Content Type and Narrative Strategy

- 主类型：Design explanation。观众需要理解如何从对象需求组织模型要素，而不是复现某个工具操作。
- 次类型：Concept boundary。用于区分 DO/IDO、属性/事件及三要素之间的职责边界。
- 本集叙事链：对象为什么还需要数字描述 → DO 与 IDO → IDO 三要素 → IDM 的抽象目的 → 属性数据三分 → 事件数据四类 → 身份/寻址/对象描述的连接 → 发动机属性识别 → 元数据定义维度 → 从对象到模型的组织顺序 → 与接口集的边界 → 结论。
- 问题闭合方式：始终围绕“一个对象怎样变成可识别数字对象”，每引入一个模型层就回答其职责；最后回到教材发动机属性任务，说明设计输入如何成为可管理的属性定义，同时明确本集没有进入接口实现。

## 6. Continuous Narration Master Script

以下 N001–N014 是本集唯一可录制口播文字来源。任何下游页面、字幕或讲者备注只能引用这些 ID，不得另写第二份口播。

[N001]
在工厂里，一台发动机、一件物料，甚至一条生产工序，都可能同时面对两种身份：现场的物理对象，以及系统里可以被查询和共享的数字对象。仅有一个编码，还不能说明对象是什么、位于哪里、经历过哪些变化。本集要回答的问题是：怎样把一个对象组织成可识别、可访问、可描述的标识数据模型？

[N002]
教材把数字对象，简称 DO，定义为数字世界中可以被唯一标识和处理的数据实体。可识别数字对象，简称 IDO，则是在网络空间中用参数、属性等信息做数字化描述，形成可访问的对象。DO 强调“可处理”，IDO 进一步回答“怎样找到并理解”。

[N003]
一个 IDO 不是把字段随意堆在一起，而是由三个相互配合的要素构成：标识编码、解析记录和对象数据。先有身份，才谈得上寻址；有了寻址，才可能取得描述对象的信息。这个三要素结构，是后面理解属性和事件的入口。

[N004]
标识编码是机器、算法以及其他物理或虚拟资源的身份符号，回答“是谁”。解析记录提供主机名与 IP 地址之间的映射以及解析服务器之间的关联，回答“到哪里找”。对象数据通过数据模型表示对象的生产、制造和使用信息，回答“它是什么”。这里讲的是职责，不是具体接口地址。

[N005]
标识数据模型，简称 IDM，是对可识别数字对象现实世界特征的模拟和抽象。它梳理对象的属性、过程和关联，形成有组织的描述，为标识对象建立贯穿生命周期的数字画像。价值不在字段越多，而在于不同系统看到同一个对象和同一套关系。

[N006]
从图示结构看，编码、解析记录和对象数据分别连接到标识注册分配、数据寻址服务和数据交互服务。由此可区分身份、位置和内容：编码不是全部数据，解析记录也不是属性表，真正承载对象描述的是对象数据及其模型。

[N007]
对象数据首先可以分成属性数据和事件数据。属性数据描述对象固有、并且能够区别于其他实体的特征，教材把它分为对象或基本数据、主体数据和位置数据。基本数据描述产品、设备或软件本身；主体数据说明对象所属的企业、机构或自然人；位置数据描述物理或逻辑位置。

[N008]
事件数据关注对象的行为、操作，以及生产、流通和使用过程中的变化。教材列出对象事件、聚合事件、交易事件和转化事件：单个对象的状态变化属于对象事件；两个或以上对象之间的打包、装配或操作可以形成聚合或转化事件；销售等流通和商业表单信息属于交易事件。图 3-6 未画出转化事件，因此这里以正文列举为准。

[N009]
把这些层次连起来：标识编码固定对象身份，解析记录提供网络寻址，对象数据再展开属性与事件。属性说明对象具有什么特征、属于谁、在哪里；事件说明对象或对象之间发生了什么变化。两者共同构成可理解的对象画像。

[N010]
这也解释了为什么模型不能只做一张静态属性表。发动机的产品名称、排量、气缸数量或适用车型，可以作为对象属性；生产、装配、流通或使用过程中的状态变化，则需要用事件来表达。属性回答“对象具有什么”，事件回答“对象经历了什么”，二者的分工比字段数量更重要。

[N011]
任务实施以发动机对象为例，先要求分析关键属性。表 3-7 给出产品编号、产品名称、排量、气缸数量、燃油类型、适用车型、特殊功能和生产日期等属性名称。这个步骤的重点不是抄一组示例值，而是从对象需求中识别哪些信息能够稳定描述对象本身。

[N012]
属性识别后，还要把属性定义成可管理的元数据。教材要求记录中文名称、英文名称、数据类型、最小长度、最大长度和是否必填；英文名以小写开头并采用组合词，类型要匹配实际取值，长度和必填性要根据属性情况设置。这样，属性才从自然语言描述进入一致的数据定义。

[N013]
到这里，本集完成的是模型设计逻辑：确认对象，安排身份和寻址，再组织属性与事件，并为属性补足定义维度。我们没有进入二级节点的 OpenAPI，也没有打开 Apifox 或讨论认证、请求和响应。那些是模型被接口承载时的另一个问题，将在后续集单独处理。

[N014]
回到开头，一个可识别数字对象要同时看见三件事：由什么身份指向，在哪里找到，用哪些属性和事件理解。把编码、解析记录、对象数据与属性、事件放在同一条链上，模型才不是孤立字段，而是对象在数字空间中的可共享描述。下一集再看它怎样进入一次 OpenAPI 请求。
